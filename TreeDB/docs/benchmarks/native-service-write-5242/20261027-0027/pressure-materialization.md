# Native write pressure: physical materialization disposition

Source-only inquiry, 2026-10-26. No product source changes or runtime. Bound to canonical HEAD `49baf47d6c3748467e08845caff0ede779f7f9c6` plus its selected staged capacity-C changes. The fixedwrite2 results are valid failures of the adoption cost gate, not accepted performance.

## Observed versus derived

Root's completed trace attributes 588.84 ms of 630.28 ms native four-writer Upsert syscall time to PrepareNativeProducerObservation; its overlapping descendants include physical flush 328.53 ms, frontier rotation 184.02 ms and journal cleanup 76.29 ms. Direct write/command completion is 41.08 ms. These are cumulative trace delays, not additive wall-time components. Pressure-associated synchronization totals across writers likewise cannot be treated as wall latency. Root's whole-process profiles include setup, Optimize, queries, reopen and Close; Upsert stack focus is not an exact benchmark-timer allocation boundary.

The source proves repeated full physical handoffs are expected under the present construction recipe. It does not establish their exact count per measured load. Existing `treedb.cache.checkpoint.runs/total_ms`, exported in caching/db.go:32398, can supply that count without a new product counter.

## Why the watermark reaches physical work

* caching/cow_native_txn.go:59-67 compares semantic ConstructionBytes with 75% of the maintenance child's original limits, independently of the global reserved-byte trigger. For the original 32 MiB child this is 25,165,824 bytes. The later Checkpoint is followed by the original semantic cleanup join; unchanged state is remembered to avoid an endless drain loop.
* collections/native_typed_engine.go:21-109 sums every pending delta's buildCapacity, schema/work controls and the captured physical manifest basis. It takes the largest applicable operation workspace once. NativeProducerPressure (:391-403) and nativeTypedEnsureConstructible (:409-418) use the same construction inventory; the latter independently enforces the full child limit before command assignment.
* collections/native_typed_materialize.go:306-341 reserves BuildCodecCapacity plus 1 MiB for ordinary JSON construction. The actual fixed amount is **13,882,752 bytes**, not 8 MiB: typedcolumn/build_codec.go:17-25 contributes 12,834,176 bytes. This is a real pinned encoder bound; it cannot be dropped because scalar granules happen to use LZ4. Image metadata sections may still use ZSTD.
* For the fixture's one typed vector column, materialize.go:272-295 prices 12,800 structural bytes per row, before source/ID bytes times six, vector backing times twelve, each member's manifest append reserve (:218-248), and captured physical manifest copies (:449-487). Seven pending 128-row batches therefore exceed the 75% trigger even using only the fixed workspace and structural-row lower bound: 13,882,752 + 7*128*12,800 = 25,351,552. Other terms can trigger earlier. This is a mathematical bound on the recipe, not an observed checkpoint cadence.
* native_source_requirements_v2.go:334-338 chooses full physical manifest capacity for ordinary cdir1, not the cdir2 streaming basis reader. Each prior physical manifest record is charged for sixteen retained/encoding/closure/mutation views. The basis grows as earlier assets remain authoritative; checkpointing removes pending typed rows but does not remove that basis.

The pressure drain is stronger than a request's durable journal ACK. caching/cow_checkpoint.go:58-162 completes prior handoff, rotates/syncs the canonical journal (:159-170), flushes value-log lanes, materializes the captured physical prefix, executes the backend durability boundary, joins accepted-prefix retirement and cleans up covered WAL. It must remain stronger: simply returning after the request ACK does not reclaim construction debt.

## What repeats, and what does not

materialize.go:753-834 selects last writers within each graph-free span, but restores original member order and invokes materializeDelta separately for every surviving member. Its selection validates **all** original (appliedLSN, memberOrdinal) ordering, including shadowed members (:646-657), then restores that order (:738-749). The immutable deltas retain these identities; physical checkpoint sequence never substitutes for them (native_typed_state.go:15-29).

Each materializeDelta closes its prior codec (:840), calls BuildColumnPublishPlan with that member's AppliedCommandLSN (:926), builds the manifest root and primary/row-locator roots (:970-1008), and advances physical metadata. Row locators embed the member plan's generation/LSN (:1059). Thus one captured checkpoint is not one asset publication. The fixture has 32 distinct public commands; unique rows cannot be discarded by last-writer selection. Exact materialization invocation counts and aborted attempts remain unmeasured here.

In column_publish_write.go:1548, native `singleOutput=true` selects isolated output. A new append session is created at :1636-1653, a fresh manager output is normally selected at :1662-1706, and the session is closed at :1823-1839. column_asset_manager.go:2417-2428 synchronously syncs the file and captures stable resources during that close. Physical durability is therefore paid separately for member asset sessions inside a checkpoint, in addition to the checkpoint's journal fences.

This is **not** evidence that every checkpoint rebuilds all old document payloads. Ordinary materializeDelta builds selected pending documents and typed rows. What it repeatedly scans/copies/validates is the growing complete manifest/resource closure and its intermediate roots. Source-import cdir2 avoids the full manifest array, but is a different source/header contract and cannot be selected by spoofing import metadata.

A particularly concrete repeated closure exists at materialize.go:1021-1027: it eagerly calls `plan.durableResourceRequirementsFallback`. stable_resource.go:222-249 already returns an append mutation plus a lazy complete-closure fallback when there are no removals. The ordinary materializer currently realizes the full closure after every member rather than preserving that lazy append proof to its final original group. Existing `SetNativeDurableResourceAppend` is already used by the source-directory lane (native_typed_engine.go:274-310). It is an available maintained authority seam, not permission to skip closure validation.

The 8,192 whole-JSON scalar decodes are a separate two-pass request cost: native_json_rows.go:552 validates each input, while :797 onward computes final scalar effects through nativeJSONFinalRowsResolved, which invokes the maintained new-state extractor again. planner.go:1817-1833 falls back to full encoding/json for this nested scalar path. Typed materialization uses already-declared rows/retained JSON; these decodes do not prove old payload materialization at every checkpoint.

## Selected next structural candidate

**Choose an original captured graph-free-span asset append session, using the existing family appender and unchanged per-member asset identities, before a general streaming-manifest redesign.** This targets the traced pressure syscall path directly. It is a source proposal only; no fit or timing claim.

The coherent boundary is the existing `materialize()` graph-free span, not a transaction-wide new owner. Build and append each member's unchanged row/typed assets under the original work, retain refs/metrics/member identity and final resource controls, and end private payload/encoder aliases after each synchronous append. Complete the original manager-owned append session once at the span boundary; only then expose immutable certified stable custody to the unchanged member manifest planners. Keep exact member order, LSN, part/generation fields and row-locator identities; no command body retry, journal recapture or new publication authority. Graph recipes remain barriers: all borrowed iterators/asset readers and pending span work must finish before the graph consumes its source. Existing failure cleanup must abort the same unpublished output and preserve ambiguity/accepted custody rules.

The prerequisite is explicit: today's PrepareAssets hook returns already-certified stable resources, and materializeDelta immediately clones them. A live mutable appender cannot masquerade as those resources. A bounded two-phase span must first append/certify using the existing session, then pass each member's prepared refs and correctly scoped immutable resource custody to its existing plan. It must not retain every encoded payload until certification, nor replace member identities with the checkpoint endpoint. The same preaccepted construction receipt must cover retained refs/control growth plus one live member constructor phase; **initial implementation must retain the original admission promise until that changed lifetime has a complete bound**. No lower coefficient follows merely from moving a Close.

This can remove repeated asset-file capture/sync work within a physical handoff. It does not by itself remove all pressure-triggered journal rotations or prove the 10x gap closes. Root's trace currently reports 163.06 ms in closeActiveWithStableValidation under Upsert; inspect its ancestors only once, not as extra time beyond physical flush.

## Alternatives and discriminator

* The smaller full-closure fix is worthwhile source-wise but attacks metadata/resource allocation and CPU, not the dominant file fences. Preserve/merge existing append mutations and defer complete closure until the final fallback is actually required; use the final manifest, original basis and original group. Destructive/update/graph paths must retain full validation. This could reduce the 14.1 MB/77,029 resource-allocation cohort, but cannot be credited with fewer checkpoint syscalls while the construction recipe/session boundary stays unchanged.
* A batch arena cannot remove File.Sync, WAL rotation, complete-closure derivation or repeated root builds. Existing batch arenas already borrow rows in bounded ordered-root batches; introducing another pool/arena would be a poor first response.
* Coalescing several members into one synthetic AppliedLSN or importing them through cdir2 is rejected. Current assets and row locators carry individual canonical identities; source-import has an additional authenticated contract. Similarly, merely raising the watermark or relaxing EnsureConstructible moves failure toward assignment without removing physical debt.
* A larger successor is one final ordered primary/locator/manifest construction per graph-free span, reusing the maintained winner selection and original per-member locators. It could avoid repeatedly rebuilding private intermediate roots. It needs a complete final-root iterator and source-generation proof, and is broader than appender lifetime reuse. It is not selected here.

Before construction, the smallest diagnostic is existing per-load Stats before request load, immediately after requests, and after Optimize: checkpoint count/time, WAL/physical frontier and live pending counts; pair with existing append FileSync/Close metrics if already surfaced. Native public `treedb.DB.Stats()` (public.go:2628) delegates to this SAME owner's cached Stats; retain its method callback in the test owner before NativeSemanticBackend, rather than calling Stats on the borrowed backend and losing cache counters. The legacy opener already has `OpenBackendWithCachedLeafLogStats` (open_backend.go:100), returning the same owner/cleanup plus its live-only Stats callback; this preserves the ordinary legacy opener policy. The current benchmark owner's struct (:95) stores only service/manager/closeDB, so adding a test-only callback is required. Query it only while the owner is live; nil/closed is unavailable, not zero. Gather maps outside the request timer. No new timed A/B is needed to learn whether a load performs several checkpoints and approximately one member asset-sync per request. A minimal temporary test-only wrapper around the existing sync observer can count manager asset syncs if existing stats omit them, without changing decisions. Preserve all samples and do not infer this count from sampled stacks.

The public discriminator for any selected implementation remains the unchanged 4096 rows / 32 requests of 128 / original one- and four-writer durable workloads, no retries, same default caps/ACK, complete Optimize/search/Close/reopen. Necessary risk cases: several original LSNs in one cut; graph barrier; insert/update/delete last-writer behavior; callback/append/certification/refusal failure at a later member; independent old-cut readers; cancellation; assigned ambiguity; no returned borrowed payload aliases; stable-resource closure and zero-owner cleanup. A focused gain cannot waive fixedwrite2's existing severe cost failure.
