# Native ANN Vector Index Proposal

Status: draft proposal, non-normative.

For the current `column_graph` typed-column graph-search prepared runtime-view
policy and type admission gate, see
`typed-column-graph-search-prepared-views.md` and
`typed-column-graph-search-admission.md`. This draft target architecture must not
override that current-format admission contract.

This document specifies a target architecture for making the TreeDB collection
ANN graph a native persisted secondary index. It replaces the current
process-local vector graph plus optional sidecar snapshot model with a
TreeDB-managed durable index that loads into memory for fast search.

The goal is the hard production version: crash-aware, rebuildable, compact,
fast on search and ingest, observable, and compatible with TreeDB collection
durability and recovery semantics.

## 1. Current State

Current collection vector search has three separate storage roles:

1. Canonical collection documents and embeddings are persistent TreeDB data.
2. `Collection.BuildVectorIndex` builds an in-memory HNSW-style graph from
   canonical rows.
3. `VectorIndex.SaveSnapshot` and `Collection.LoadVectorIndexSnapshot` can
   persist and load immutable graph snapshots under sidecar
   `vector_indexes/<collection>/<index>/` files.

Incremental collection writes can notify a registered in-memory vector index,
but the graph is not currently a native TreeDB secondary index. It is not
automatically recovered as part of collection open unless callers explicitly
load a snapshot or rebuild.

## 2. Goals

1. Treat ANN vector indexes as first-class collection secondary indexes.
2. Persist ANN graph state inside TreeDB-managed storage, not as JSON sidecar
   snapshots.
3. Preserve canonical collection rows as the source of truth for documents and
   exact rerank.
4. Load a compact in-memory runtime graph for query execution.
5. Keep write acknowledgment semantics coherent with collection durability.
6. Support crash recovery without silently serving a stale index.
7. Support incremental insert/update/delete maintenance.
8. Support batch rebuild, compaction, tombstone cleanup, and format evolution.
9. Keep 10k to multi-million document indexes operationally observable.
10. Provide benchmarks and profile artifacts that compare TreeDB ANN against
    in-memory controls such as USearch with explicit apples-to-apples labels.

## 3. Non-Goals

1. Direct disk traversal for every ANN search is not the primary design.
   Native persistence must not force search to become random I/O bound.
2. Vector embeddings are not generated by TreeDB.
3. Exact vector search remains a correctness fallback, not the target fast
   path for broad unfiltered queries.
4. Distributed or Raft replication is out of scope except for deterministic
   record formats and future replay compatibility.
5. Cross-version migration scaffolding is not required while TreeDB remains
   pre-alpha, but unsupported formats must fail closed.

## 4. Target Architecture

The native ANN index has two representations:

1. Durable representation:
   TreeDB-managed index records stored in collection/index keyspaces.
2. Runtime representation:
   an in-memory graph optimized for search and incremental maintenance.

Open path:

```text
DB open
  -> collection catalog open
  -> vector index catalog enumerate
  -> load durable ANN records into runtime graph
  -> validate epoch/applied sequence/currentness
  -> register index for reads and write notifications
```

Write path:

```text
collection mutation batch
  -> write canonical rows
  -> extract vector deltas
  -> update durable ANN records and runtime graph
  -> publish collection/index visibility atomically or mark index catch-up state
```

Search path:

```text
query vector
  -> validate dimensions/metric
  -> prepare query norm
  -> search runtime graph under RLock
  -> fetch canonical rows for exact rerank unless caller uses graph-only
  -> return results with trace/status
```

The durable records are the persisted secondary index. The runtime graph is a
cache of that persisted index, but it is required for fast operation and is
loaded automatically.

## 5. Durable Keyspaces

Use collection-local TreeDB roots or native collection index roots. Exact root
integration depends on the collection native fast-path work, but logical
keyspaces should be stable:

```text
vi/{collectionID}/{indexID}/config
vi/{collectionID}/{indexID}/state
vi/{collectionID}/{indexID}/epoch/{epoch}/meta
vi/{collectionID}/{indexID}/epoch/{epoch}/node/{nodeID}
vi/{collectionID}/{indexID}/epoch/{epoch}/edge/{nodeID}/{layer}
vi/{collectionID}/{indexID}/epoch/{epoch}/doc/{documentID}
vi/{collectionID}/{indexID}/epoch/{epoch}/tomb/{nodeID}
vi/{collectionID}/{indexID}/delta/{collectionSeq}/{mutationOrdinal}/{deltaOrdinal}
vi/{collectionID}/{indexID}/deltaBatch/{collectionSeq}/{mutationOrdinal}
vi/{collectionID}/{indexID}/rebuild/{runID}/...
```

If collection roots are available as native ordered roots, each logical
keyspace SHOULD map to a dedicated root or prefix within a single vector-index
root. The implementation should avoid storing large graph records inside the
collection primary document root.

The `config` record contains stable index identity and options. The `state`
record publishes the currently readable epoch. Epoch metadata, node, edge,
document map, and tombstone records MUST be scoped by epoch so rebuilds and
compaction can write a complete staging epoch without overwriting the active
graph. Publishing a new epoch in `state` is the atomic visibility boundary;
readers load epoch-scoped metadata from the published epoch and never combine it
with metadata from another epoch. Old epochs are retained until active readers
drain and then reclaimed.

Delta and `deltaBatch` records intentionally span epochs. They are ordered by
collection sequence, not graph epoch, so recovery and rebuild catch-up can replay
all mutations after an epoch's `applied_collection_seq` or `rebuild_cut_seq`
into whichever staging epoch is being prepared.

Numeric path segments use fixed-width big-endian bytes in native key encoding:
`epoch` and `nodeID` are `u64`, `layer` is `u16`, `collectionSeq` is `u64`,
`mutationOrdinal` is `u32`, and `deltaOrdinal` is `u32`. This preserves ordered
iteration for prefix scans such as all edge records for a node or all deltas
after an applied collection sequence. Human-readable paths in this document are
illustrative; the native codec MUST use the canonical byte ordering.

## 6. Record Model

### 6.1 Metadata Record

```text
magic: "TVI1"
format_version: u16
feature_flags: u64
collection_id: bytes
index_id: bytes
index_name: bytes
field_path: repeated bytes
metric: enum { cosine, l2_squared, inner_product }
encoding: enum { float32, int8, future }
dimensions: u32
m: u16
ef_construction: u32
ef_search: u32
entry_node_id: u64, all-ones sentinel 0xFFFFFFFFFFFFFFFF means no entry node
max_level: u16
next_node_id: u64
live_count: u64
deleted_count: u64
index_epoch: u64
applied_collection_seq: u64
build_id: fixed 16 bytes
state: enum { ready, building, catching_up, dirty, needs_rebuild, disabled, missing }
```

The metadata record MUST be validated before serving graph search. Unknown
required feature flags MUST fail closed. `missing` is a synthetic open-time
state used when no native ANN metadata has been published yet. The all-ones
`entry_node_id` sentinel is reserved and MUST NOT be allocated as a durable
`node_id`; `next_node_id` must stop before that value.

### 6.2 Node Record

```text
node_id: u64
document_id: bytes
level: u16
flags: bitset { deleted, quantized, normalized, stale }
vector_encoding: enum
vector_payload: bytes
quant_scale: f32 optional
norm_squared: f64
inverse_norm: f32
created_seq: u64
deleted_seq: u64 optional
```

For float32 vectors, `vector_payload` is `dimensions * 4` little-endian bytes.
For int8 vectors, it is `dimensions` bytes plus quantization metadata.

The durable ANN node stores a vector copy because graph search needs dense
sequential access. Canonical rows remain the source of truth for rerank and
rebuild. A future pointer-only mode MAY exist, but it is not the fast production
target.

### 6.3 Edge Record

```text
node_id: u64
layer: u16
neighbors: repeated {
  neighbor_node_id_delta_or_id: u64 varint
  cached_distance: f32 or quantized_distance
}
crc_or_record_checksum: optional
```

Edges SHOULD be stored by source node and layer. Within one edge record,
neighbor IDs SHOULD be sorted for compact delta encoding if deterministic
ordering does not regress HNSW behavior. The first neighbor ID is encoded as an
absolute unsigned varint; each subsequent neighbor ID is encoded as an unsigned
delta from the previous sorted neighbor ID. The runtime graph may keep insertion
or distance order separately if needed, but the durable codec uses this one
canonical form.

Cached edge distances are part of the target format. They remove repeated
node-to-node scoring during pruning and rebuild operations.

### 6.4 Document Map Record

```text
document_id -> current_node_id
```

This map is required because updates create new nodes and tombstone old nodes.
Search must ignore graph nodes that are not the current node for a document.

### 6.5 Tombstone Record

```text
node_id -> deleted_seq, document_id, reason
```

The node record MAY also contain the deleted bit, but a tombstone keyspace makes
rebuild planning, GC, and stats cheaper.

### 6.6 State Record

```text
index_epoch
applied_collection_seq
applied_mutation_ordinal
dirty_reason
last_rebuild_duration
last_rebuild_seq_range
pending_delta_count
deleted_ratio
```

This record is the recovery decision point. It determines whether the runtime
index can be served, must catch up, or must rebuild. The applied watermark is
the pair `(applied_collection_seq, applied_mutation_ordinal)`, not the
collection sequence alone, because buffered writes can acknowledge multiple
mutation boundaries before the collection root sequence advances.

### 6.7 Delta Log Record

```text
collection_seq: u64
mutation_ordinal: u32
delta_ordinal: u32
document_id: bytes
op: enum { insert, update, delete }
new_node: node payload optional
old_node_id: u64 optional
vector_present: bool
checksum: optional
```

Buffered mode appends one delta record per document-level vector mutation that
has not yet been applied to the durable graph epoch. Batched collection writes
can share one `collection_seq`, so each emitted delta in that mutation boundary
MUST get a deterministic zero-based `delta_ordinal`. Buffered collection writes
can also acknowledge multiple mutation boundaries before the collection root
sequence advances, so each acknowledged boundary under the same `collection_seq`
MUST get a durable `mutation_ordinal` before acknowledgment. Delta records are
ordered by `(collection_seq, mutation_ordinal, delta_ordinal)` and are replayed
strictly in that order during catch-up or crash recovery. Once the state
watermark is at or beyond a delta's `(collection_seq, mutation_ordinal)` and the
publishing epoch is durable, deltas for that mutation boundary are eligible for
cleanup. Cleanup MUST NOT delete all deltas for a collection sequence unless
every mutation boundary in that sequence is proven applied. If a delta is
missing, corrupt, or not replayable, recovery marks the index `needs_rebuild`
instead of serving graph search as current.

### 6.8 Delta Batch Boundary Record

```text
collection_seq: u64
mutation_ordinal: u32
delta_count: u32
checksum: optional
```

For every collection mutation boundary, including single-document writes,
`InsertBatch`, and `UpdateBatch`, the index writer MUST persist all delta records
for that `(collection_seq, mutation_ordinal)` and then persist one boundary
record with the exact `delta_count`. Recovery MUST NOT advance
`applied_collection_seq` past a sequence unless every mutation boundary for that
sequence has a boundary record and each durable delta set contains every ordinal
in `[0, delta_count)`. A missing boundary or truncated ordinal range means the
durable ANN state is incomplete; recovery must keep the index catching up if the
canonical collection log can supply the missing work, otherwise mark
`needs_rebuild`.

## 7. Runtime Representation

The runtime graph should remain close to the current optimized shape:

```text
type VectorIndex struct {
    nodes       []vectorIndexNode
    currentNode map[string]int
    entry       int
    maxLevel    int
    searchScratch sync.Pool
}

type vectorIndexNode struct {
    documentID []byte
    vector []float32 // or quantized []int8 when Encoding is int8
    quantized []int8
    normSquared float64
    cachedInvNorm float32
    level int
    neighbors [][]vectorIndexNeighbor
    deleted bool
}

type vectorIndexNeighbor struct {
    nodeID int
    distance float32
}
```

The runtime graph MAY use narrower types than Go `int` internally after the
format stabilizes. For example, `uint32` node IDs are sufficient until a single
index exceeds four billion nodes, and using them with a `float32` distance can
cut edge memory in half. The runtime representation MUST switch to a wider node
ID representation before any durable `node_id` exceeds `math.MaxUint32`; it must
never wrap or truncate durable `u64` node IDs.

## 8. Write Semantics

### 8.1 Strong Mode

In strong mode, a collection mutation is acknowledged only after both
canonical row changes and ANN index changes are durable according to the
collection durability mode.

Required behavior:

1. Insert/update writes canonical document bytes.
2. Vector extraction produces zero or more document-level vector index mutations
   per affected vector index. Batch writes may emit multiple mutations under the
   same collection sequence.
3. ANN durable records are updated in the same publish group or recovery unit.
4. Runtime graph is updated after durable intent is staged and before the
   write becomes visible to graph search.
5. Crash recovery either observes both document and index changes or marks the
   index dirty/catching_up before serving graph search.

Strong mode is easiest to reason about but can make write latency depend on
HNSW insertion cost.

### 8.2 Buffered/Catch-Up Mode

In buffered mode, collection writes can acknowledge after canonical durability
while a durable vector-index delta log records pending ANN work.

Required behavior:

1. The index state MUST be `catching_up` or `dirty` while unapplied deltas
   exist.
2. Search MAY use the graph only if the caller accepts bounded staleness and
   the trace reports it.
3. Default public search MUST use exact fallback or a delta-aware merge that
   includes current vectors from unapplied inserts and updates. Reranking only
   the stale graph candidates is not sufficient because acknowledged vectors may
   be absent from the graph candidate set.
4. Recovery MUST replay pending vector deltas or mark `needs_rebuild`.

Buffered mode is the likely high-throughput production default for large batch
ingest, but the visible status must be explicit.

### 8.3 Update and Delete

Updates SHOULD create a new node and tombstone the old current node rather than
attempting in-place graph rewiring. This matches current behavior and keeps
write complexity bounded.

Deletes mark the current node deleted, remove the doc map entry, and increment
deleted counters. Physical cleanup occurs during vector index rebuild/GC.

## 9. Recovery Model

Recovery MUST never silently serve a stale ready index.

At open:

1. Load collection catalog and collection sequence/watermark state.
2. Load vector index metadata and state.
3. If format or feature flags are unsupported, fail closed for that index.
4. If `applied_collection_seq` matches the collection root sequence, load the
   graph as `ready`.
5. If a durable delta log exists, replay it into durable records and runtime
   graph, then publish `ready`.
6. If records are incomplete or checksums fail, mark `needs_rebuild` and route
   default search to exact fallback.
7. If rebuild policy allows open-time repair, rebuild from canonical collection
   rows and atomically publish a new index epoch.

Index state transitions:

```text
missing -> building -> ready
ready -> catching_up -> ready
catching_up -> dirty -> needs_rebuild
catching_up -> needs_rebuild
dirty -> catching_up -> ready
dirty -> building -> ready
ready -> dirty -> needs_rebuild -> building -> ready
ready -> needs_rebuild -> building -> ready
ready -> disabled
catching_up -> disabled
dirty -> disabled
needs_rebuild -> disabled
disabled -> building
```

`dirty` means correctness requires exact fallback or repair. `needs_rebuild`
means incremental replay is insufficient or unavailable.

## 10. Rebuild, GC, and Compaction

Rebuild creates a new index epoch from canonical rows:

```text
pin collection snapshot and record rebuild_cut_seq
scan canonical collection rows
  -> extract vectors
  -> build runtime graph
  -> write durable node/edge/docmap records to staging root/epoch
  -> verify counts/checksums/recall smoke
  -> replay or merge vector deltas after rebuild_cut_seq
  -> atomically publish metadata entry and state=ready once caught up
  -> retire old epoch after readers drain
```

A background rebuild or compaction MUST pin a collection snapshot cut before it
scans canonical rows. Writes acknowledged after `rebuild_cut_seq` must either be
blocked until publish, replayed from the durable delta log into the staging
epoch before publishing `ready`, or leave the published state as `catching_up`
until those deltas are applied. A rebuilt epoch must not replace a current graph
with a scan that silently missed acknowledged writes.

GC compacts tombstoned nodes:

1. Build a new node ID mapping for live nodes.
2. Rewrite node records, edge records, doc map, and metadata.
3. Drop tombstoned node records after the new epoch is published.

Rebuild SHOULD trigger when:

- deleted ratio exceeds `RebuildDeletedRatio`,
- graph validation fails,
- vector-index options change,
- encoding changes,
- catch-up delta count exceeds a configured threshold,
- recall smoke falls below configured gate.

## 11. Search Semantics

Default `VectorIndex.Search` uses:

1. runtime ANN graph for candidate generation,
2. current doc map and tombstone validation,
3. canonical row fetch and exact rerank,
4. exact fallback if graph is missing, dirty, or underfilled.

Graph-only search remains benchmark/internal unless explicitly exposed as an
unsafe or diagnostic API. It MUST report that it bypasses canonical row fetch
and exact rerank.

If runtime graph is unavailable but durable records are present, TreeDB SHOULD
load the runtime graph before serving ANN. Direct on-disk graph traversal is a
future specialized mode, not the baseline.

## 12. Concurrency

Runtime graph concurrency:

- Searches take `RLock` and use per-goroutine scratch from `sync.Pool`.
- Incremental graph mutation takes `Lock`.
- Rebuild builds off to the side and swaps the runtime pointer under a short
  write lock.
- Long durable writes and staging MUST NOT hold the search lock.

Production target:

```text
atomic pointer to current runtime graph
  + immutable graph epoch for readers
  + writer builds/mutates next graph or applies serialized deltas
  + epoch reclamation after readers drain
```

This allows high search concurrency and avoids blocking searches on long
rebuilds.

Parallel execution opportunities:

1. Independent queries already scale through shared immutable graph reads.
2. Rebuild can parallelize vector extraction and staged record encoding while
   preserving deterministic graph insertion order.
3. Sharded vector indexes MAY be introduced later for parallel build/search,
   but they change recall behavior and require a separate spec gate.

## 13. Compression and Encoding

Use compact binary records, not JSON, for native persistence.

Recommended first format:

- node vectors: little-endian float32 or int8 quantized bytes,
- edge neighbor IDs: varint or delta-varint,
- edge distances: float32 initially, optional uint16 quantized later,
- document IDs: prefix-compressed by ordered key layout,
- page/block compression: reuse TreeDB page/value compression where available.

Expected size for 10k docs x 64 dims, `M=16`, using binary MiB
(`1 MiB = 1024 * 1024 bytes`) and an illustrative average of about 37 directed
edges/node. The 37-edge estimate is a sizing placeholder derived from a base
layer near `2*M` plus a small upper-layer average for benchmark-sized HNSW
graphs; it should be replaced with measured fanout once the native format lands:

```text
float32 vectors: ~2.44 MiB
edges as uint32+float32: ~2.82 MiB
node/doc metadata: ~0.5-1.0 MiB before TreeDB overhead
```

With compact binary plus page compression:

```text
float32 mode: roughly 4.5-6.5 MiB effective
int8 mode:    roughly 2.5-4.5 MiB effective
```

Generic compression will not shrink normalized float32 vectors much. Format
choice matters more than codec choice.

## 14. Public API Target

Proposed API shape:

```go
type CreateVectorIndexOptions struct {
    Name string
    Field string
    Metric VectorMetric
    Dimensions int
    M int
    EfConstruction int
    EfSearch int
    Encoding VectorIndexEncoding
    Durability VectorIndexDurabilityMode
    Maintenance VectorIndexMaintenanceOptions
}

func (c *Collection) CreateVectorIndex(opts CreateVectorIndexOptions) (*VectorIndex, error)
func (c *Collection) OpenVectorIndex(name string) (*VectorIndex, VectorIndexLoadStatus, error)
func (c *Collection) DropVectorIndex(name string) error
func (idx *VectorIndex) Rebuild(ctx context.Context, opts VectorIndexRebuildOptions) (VectorIndexRebuildStatus, error)
func (idx *VectorIndex) Compact(ctx context.Context, opts VectorIndexCompactOptions) (VectorIndexCompactStatus, error)
func (idx *VectorIndex) Status() VectorIndexStatus
```

Existing `BuildVectorIndex`, `SaveSnapshot`, and `LoadVectorIndexSnapshot` MAY
remain as compatibility or test helpers during transition, but native index
creation should become the production path.

`OpenVectorIndex` returns `VectorIndexLoadStatus` separately so callers can
decide whether to use exact fallback before invoking methods on a partially
loaded, catching-up, or rebuild-required index. `idx.Status()` exposes the same
state after open.

## 16. Verification Plan

### 16.1 Unit Tests

1. Metadata validation rejects incompatible dimensions, metrics, encodings, and
   feature flags.
2. Node encode/decode round trips float32 and int8 vectors.
3. Edge encode/decode preserves neighbor IDs and cached distances.
4. Doc map update points to newest node after update.
5. Tombstone update removes document from current map.
6. Runtime graph loaded from durable records matches expected search results.

### 16.2 Reopen Tests

1. Create index, insert docs, close, reopen, search without manual rebuild.
2. Insert/update/delete with index enabled, checkpoint, reopen, verify search.
3. Save while dirty/catching-up, reopen, verify state and fallback behavior.
4. Reopen with missing edge records marks `needs_rebuild`.
5. Reopen with old unsupported feature flags fails closed.

### 16.3 Recovery Tests

1. Simulate crash after canonical row write before ANN update.
2. Simulate crash after ANN durable delta before runtime apply.
3. Simulate crash during rebuild staging before publish.
4. Simulate crash after new epoch publish before old epoch cleanup.
5. WAL-on and WAL-off relaxed modes must have explicit expected behavior.

### 16.4 Concurrency Tests

1. Concurrent searches during incremental inserts.
2. Concurrent searches during background rebuild/swap.
3. Race test for runtime graph pointer swap and reader epoch reclamation.
4. Drop index while readers are active.

### 16.5 Benchmark Gates

Maintain benchmark matrix:

- graph-only ANN search,
- full indexed search with canonical rerank,
- build from existing collection,
- incremental write with index,
- reopen/load index,
- rebuild/compact,
- memory bytes,
- durable bytes,
- recall-at-k.

For each run, compare:

- TreeDB native ANN,
- TreeDB exact search,
- optional USearch in-memory control.

Tables MUST label whether each number includes persistent collection writes,
document fetch, exact rerank, or only in-memory ANN.

## 17. Implementation Plan

### Phase 0: Freeze Baselines and Invariants

Deliverables:

1. Baseline current #1526 performance:
   - graph-only search,
   - full search,
   - build,
   - incremental write,
   - snapshot save/load,
   - memory and disk bytes.
2. Add native index design tests as skipped or TODO-gated tests where useful.
3. Add a benchmark report template that labels apples-to-apples boundaries.

Acceptance:

- Existing vector tests pass.
- Baseline artifacts are attached to the tracking issue.

### Phase 1: Binary Record Codecs

Deliverables:

1. Implement binary codecs for metadata, node, edge, doc map, tombstone, delta,
   and state records.
2. Add golden encoding fixtures.
3. Add fuzz tests for decode rejection.
4. Add size benchmarks for float32 and int8 modes.

Acceptance:

- Round-trip and malformed-input tests pass.
- Golden fixtures are stable.
- Codec allocs are bounded and visible in benchmarks.

### Phase 2: Durable Native Storage Layout

Deliverables:

1. Create vector-index logical roots/keyspaces.
2. Write durable records from an existing runtime graph.
3. Load runtime graph from durable records.
4. Keep sidecar snapshot code untouched during bring-up.

Acceptance:

- Create/build/persist/load works in one process.
- Close/reopen/search works without `SaveSnapshot`.
- Missing/corrupt records produce `needs_rebuild` or exact fallback.

### Phase 3: Catalog and Open Integration

Deliverables:

1. Store vector index definitions in collection catalog/index metadata.
   Each declaration carries a `schema_generation` assigned when the index is
   created so stale pre-root runtimes cannot publish into a dropped/recreated
   declaration with the same name and root ID `0`.
2. Auto-open native vector indexes with collections.
3. Register loaded indexes for search and write notifications.
4. Add `CreateVectorIndex`, `OpenVectorIndex`, and `DropVectorIndex`.

Acceptance:

- User does not call manual load after reopen.
- Dropping an index removes catalog state and durable index records.
- Unsupported format fails closed.

### Phase 4: Incremental Durable Maintenance

Deliverables:

1. Apply insert/update/delete deltas to durable records and runtime graph.
2. Add doc map and tombstone durable updates.
3. Add `applied_collection_seq` and state transitions.
4. Implement strong mode and dirty/catch-up mode behind options.

Acceptance:

- Insert/update/delete survive reopen.
- Simulated partial-update recovery never serves stale ready graph.
- Search trace reports exact fallback when state is not ready.

### Phase 5: Rebuild and Compaction

Deliverables:

1. Build new index epoch from canonical rows.
2. Atomically publish new epoch.
3. Compact tombstoned nodes and rewrite node IDs.
4. Retire old epochs after readers drain.

Acceptance:

- Rebuild preserves search behavior and improves deleted ratio.
- Crash during rebuild leaves either old ready epoch or new ready epoch.
- Compaction lowers bytes and tombstone count.

### Phase 6: Fast Runtime Loading

Deliverables:

1. Load durable records into pre-sized arrays.
2. Decode edge records in layer order.
3. Use compact runtime edge/node ID types where safe.
4. Add load-time checks for graph invariants.

Acceptance:

- Reopen/load time is benchmarked and bounded.
- Runtime search performance remains within 5-10% of current in-memory graph.
- Memory accounting includes realistic runtime overhead.

### Phase 7: Background Maintenance

Deliverables:

1. Background rebuild trigger based on tombstone ratio and dirty state.
2. Optional catch-up worker for buffered mode.
3. Admin/status APIs and logs.
4. Backpressure when pending deltas exceed limits.

Acceptance:

- Large ingest can proceed without unbounded memory/delta growth.
- Maintenance state is observable and testable.

### Phase 8: Deprecate Sidecar Snapshots

Deliverables:

1. Keep `SaveSnapshot`/`LoadVectorIndexSnapshot` as compatibility tools or
   remove them if no longer needed.
2. Document migration path while TreeDB is pre-alpha.
3. Update README and spec ownership docs.

Acceptance:

- Native index path is the documented production path.
- Sidecar snapshots are clearly legacy/diagnostic if retained.

## 18. Risk Register

| Risk | Mitigation |
|---|---|
| Write latency regresses from synchronous HNSW insert | Offer buffered durable delta mode and batch rebuild path. |
| Stale graph served after crash | State machine, applied sequence checks, fail-closed open, exact fallback. |
| Memory grows from cached edge distances | Compact runtime types, optional quantized distances, rebuild/compaction. |
| Durable format is too large | Binary records, varint edge IDs, int8 vector encoding, page compression. |
| Rebuild blocks searches | Build new epoch off to the side and atomically swap runtime graph. |
| Recall changes from sharding or batching | Keep unsharded HNSW as baseline; gate sharding separately. |
| Index update and collection row diverge | Common publish/recovery unit or durable delta log with explicit dirty state. |

## 19. First Three PRs

Recommended initial PR sequence:

1. Add binary record codecs and golden tests.
2. Add native durable write/load path for complete graph epochs, without
   incremental maintenance.
3. Wire collection catalog/open to auto-load native vector indexes and exact
   fallback on invalid state.

Only after those land should incremental durable maintenance be implemented,
because recovery semantics depend on having a reliable durable epoch format and
catalog state.
