# Selected native private control capacity design

Recommend **a freelist-local append-only uint64 set backed by an explicitly sized slice**, only for the captured private changed/replaced controls, the independent metadata-reuse planning replacements, and the validation sink IDs. Reuse the existing producer Owner, finite allocation/copy work and typed removal mechanisms. Do not move canonical live/successor maps, change the ordinary map implementation, or extract the general identity registry for this repair. This is a concrete design option for root to select, not an implemented or accepted source repair, runtime grant, complete retained bound, or Q32 progress result.

## Smallest coherent representation and dispatch

A proposed `freelist/private_control_capacity_v6.go` can contain an unexported storage type with `ids []uint64`, actual backing charge, and only the in-flight new backing/copy index and removal state needed by its original mutation/cleanup. IDs are append-only, unique, and never require deletion while active. Empty means nil backing/zero charge; chunk key0 is legal, so avoid a zero-key sentinel. Use explicit `make` capacities and checked multiplication, never an implicit append growth. Physical backing charge is `retainedalloc.AllocationCharge(capacity * sizeof(uint64))`; it is an existing conservative allocation policy, not a guessed Go-map heap formula.

Prefer embedding the three primary controls in existing COWPreparationWorkV6 storage and the independent planned replacement control in metadataReuseWorkV1. Bind them to the SAME Owner supplied by BindRetainedOwnerV6 before Step. Carry a small typed private view through original work methods, bound to the exact private txn, rather than adding sets/RemovalWork to FreelistTxn and then copying them with `planned=*t`. Keep the FreelistTxn and CandidatePageSink layouts and ordinary fields intact if this explicit-view route is used. A nil view keeps the existing map path, including ordinary and canonical successor work. Selected native controls must have nil maps: never keep native map+slice copies together.

Concretely: an optional private view can be passed to private variants of marker, prune, inventory and materialization methods, with existing wrappers selecting the unchanged map route. `stateMapInsertWorkV1.step` may dispatch to a typed private-set cursor when explicitly supplied that view, or a separate private insert cursor may be embedded alongside it; **w!=nil and privatePreparation are not valid selectors**. The latter flag is deliberately revoked during materialization. The map field address cannot be reinterpreted as slice storage. Bind exact set identity, key, current count/version and phase; resets such as `s.marker = candidateBeginWorkV1{}` must not silently lose private dispatch on the next call.

`FreelistTxn.valid` currently requires changedChunks!=nil (`generation_v1_txn.go:263`). Do not weaken that ordinary invariant globally or create a dummy native map. Materialization's private entry must validate its exact bound view plus the same base/root/consumed conditions; its public/unbound path still uses the original valid check. Native changed counts/stats/inventory must read the selected private set. SourceLocked/live profile reads remain canonical map reads. Audit the short temporary a.cow.txn adoption cut for map assumptions: the frozen activation path transfers fields without enumerating these maps; no public call may return with that temporary slot installed.

The sink need not acquire another independently allocated header or alter its ordinary map API. The private view can live on the original recording work, refer to the preparation-owned sink-ID set, and require the actual embedded sink's map to remain nil. Ordinary/custom-sink work retains its original path. Selected native writes must never invoke ordinary WritePage on that nil-map sink. Duplicate semantics differ: txn inserts are idempotent; a repeated sink ID is ErrGenerationFormat. The saved write phase must recognize its own already committed insert after a later refusal, rather than rejecting itself as a new duplicate. Preserve original tail-write-attempt/burn and first-error ordering; the current duplicate probe already follows markTailWriteAttempted.

## Work, growth overlap and cleanup

Membership in an unsorted slice is worst-case O(n); building n unique IDs by individual insertion is O(n²) comparisons. Enumeration and copying are O(n). This buys a simple explicit backing/lifetime, not an asymptotic or measured performance improvement. Each comparison/read, copy/write and header/phase change requires its actual finite reservation. A private immutable scan can retain an index across calls; an unrelated key, set, count/version or operand change must reject reuse of that cursor. Capturing a canonical mutable map is different: preserve the current **whole locked copy** at `allocator_preparation_work_v6.go:223–241`, including its preadmitted visits and fresh-unit refusal. No map iterator can survive unlock while ordinary writers mutate it; do not replace that copy with a cross-call reflect.MapIter or ordinal restart over randomized map order.

Existing stateMapInsertWorkV1 (`generation_v1_begin_work.go:34–78`) is useful cursor discipline: retain the completed probe so a fresh quantum can fund the insertion. Its 256+128*(count+1) map mutation work bound is not retained-capacity provenance. Keep its map branch and canonical successor boundary test unchanged. For the new private representation, choose checked explicit capacity growth, for example the existing `AppendWork` geometric pattern at `append_work.go:67–77`; state the actual selected capacity. Do not treat inherited input/resource/file caps as an unstated maximum set cardinality.

A coherent finite grow sequence is: (1) preadmit actual new slice allocation/zeroing work and use AddPendingWithOrdinalWork on the SAME owner for the **entire new Q(cap*8)** while old remains charged; only after successful admission allocate and record the new backing/charge; (2) copy old IDs through admitted incremental slots, with no mutation allowed on this set meanwhile; (3) reserve the exact swap/insert/header work, install new backing, and drop every old data alias; (4) finish old charge removal through an embedded original RemovePendingWork cursor. The two actual arrays are counted separately while both exist. New-header allocation must not hide input-sized copy work. A cursor may retain private construction state across calls, never a lock, a live map iterator or unused permission to perform work later. If work to allocate the backing alone exceeds a fresh byte quantum, refuse explicitly before allocation; do not widen limits.

Finish the current insert's post-commit removal before reusing its cursor or starting another growth. False after commit must remain a distinct phase so the key is not inserted twice and debt is not removed twice. On cancellation before swap both arrays are private; clear all data aliases then remove each original charge exactly once. After swap the old scalar refund debt may remain while the old array has no alias: distinguish this accounting debt from a physical-union row. Copying a live RemovalWork or overwriting it during replanning is invalid. Reinitialize only after its operation is complete and quiescent.

Use the existing normalization releaseScratch pattern (`generation_v1_reservation_inventory_work.go:297–316`): clear aliases first, then resumable removal, with owner/amount/state surviving a refusal. Extend both COWPreparationWorkV6.Cancel and ClosePublishedWithWorkV6; ClosePublished still validates publication+activation and never calls Cancel on a published candidate. Detach marker/materialize/inventory/planned/recording views before refund; keep charges and removal state reachable until done. Either clear the sink set's entire view inside the preparation (outer embedded sink keeps no slice pointer), or defer its refund until the outer original reset. The first choice minimizes cross-package cleanup changes. Terminal cleanup must be legal after stale-source refusal, partial capture, partial copy, duplicate/error, or failed metadata planning, and must preserve canonical output/root/record/page aliases.

## Why neither existing helper is a drop-in

`registry_capacity.go` supplies the maintained capacity/overlap pattern, but its linear probes, full rehash and clear loops are ordinary unbounded operations; set uses ordinary Owner.Add and Remove. It also carries StableIdentity payload/clone/hash callbacks. `IdentityCapacityTable.Next` can walk arbitrary empty cells without finite admission. Rootpublication already depends on freelist, so importing these types back creates a cycle. A true storage-only extraction to a lower package is possible, but requires a callback-free uint64 specialization or generic core, finite probe/rehash continuations, work-bearing owner seams, and regression controls for every existing registry use. That is larger than these four append-only private sets; avoid coupling this repair to it.

`reservationInventoryWorkV1` supplies admitted copy/enumeration and normalization techniques, but its vector is built after transaction consumption and becomes canonical DATA output. It is not available for earlier membership/mutations; sorted/coalesced extents are not a live unique-ID table. Reusing that output vector as the mutable private set would mix lifetimes and create an output alias. Its new private branch should enumerate the set by index, preserving frozen txn/root/count checks; the ordinary reflect/map branch stays unchanged.
