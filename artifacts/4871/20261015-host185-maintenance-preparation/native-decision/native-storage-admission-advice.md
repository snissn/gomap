# Native storage admission — independent source advice

Recommend the two native-only changes together, with a **one-attempt Linux sync adapter selected at both index barriers and the capsule fence**. These remove the identified mutable dirty-geometry and verifier-retry terms without changing owners or borrowing an ordinary completion. This is conditional design advice, not acceptance of current source, a computed final-turn total, Q32/1MiB qualification, or a runtime grant. Reviewer: explicitly routed gpt-6.1-sol/high; no children, source/Git/GH edits, builds, tests or runtime. Exact inspected source bytes are bound in the accompanying JSON; the source writer remains sole owner.

## A. Conservative verified-word invalidation

`pager/write_work.go:135-147` and `:280-292` currently clear the target mask with a charged CAS retry loop. Concurrent `Pager.MarkVerified` (`pager.go:620-630`) updates other bits without taking pager.mu, so holding the writer mutex does not bound retries. The original immutable word backing is already obtained and capacity checked under p.mu; a native-only `atomic.StoreUint64(word,0)` on that same word is a fixed source operation. Zero means unverified, never a fabricated verification. Concurrent MarkVerified either wins before the store and loses a cache hit, or retries/marks a page it really verified afterward. No new bitmap, copied directory or owner is required.

This conservatively evicts up to63 neighboring cached verifications (up to62 for a pair,61 for a three-page span). It can add later checksum work and contention to other readers. That is a real cross-reader cost to retain in performance qualification, not free work because it occurs after the native call. Existing checksum/immutable-page semantics must still prohibit concurrent reads/reuse of the actual write targets; Store0 does not repair a target being modified while another reader verifies it. The old masked CAS already relies on that target-ownership condition. Neighboring immutable pages remain correct when their bits are cleared. Do not use atomic.And as a purported retry-free replacement: the pinned amd64 And64 implementation uses CAS.

Select the mode explicitly on the SAME shared physical write core. The actual native metadata chain is `materializePrimarySealWithWorkV6` (`db/primary_materialization_work_v6.go:16-55`) → candidate `WritePagesToPagerWithWorkV6` → `WriteCandidatePageToPagerWithWorkV6` (`freelist/generation_v1_format.go:72`) → pager write. A native-specific pager entry/mode can share that core while ordinary `WriteWithWork` keeps its masked CAS. The typed native capsule entry (`write_work.go:379`) must select the same conservative mode; ordinary capsule/pair/callback entries stay unchanged. Do not infer native mode from work!=nil: other work-bearing callers are not thereby native. Keep original pre-copy admission, dirty membership marking, exact destination and mutation flag ordering. No charge may later refuse after an earlier irreversible effect merely because this local CAS was removed.

## B. Same retained Linux file fence, without dirty snapshotting

Current `stablePagerOwnedOperations.SyncThroughWithWorkV6` (`db/stable_pager_owned_operations.go:90-100`) dispatches the original token's retained FD to `SyncIndexDataWithStableFileAtPathWithWorkV6`. That still calls the ordinary snapshot engine (`pager.go:1121`): count/span pricing, takeFrom, allocation, detachment, variable restoration, and potentially workers. A dirty count forecast taken before unlocked I/O cannot bound later ordinary writes.

On Linux, the repository's existing mapped-write policy and specification say the file data barrier covers mmap writes (`mmap_sync_policy_linux.go`; spec/write-path-and-durability.md:59-67). Therefore the native-only barrier can reserve its actual fixed operands first, take original p.mu.RLock, issue the actual retained-file fence, observe extent on the SAME FD and update durableFileSize while still under that lock, then unlock. It must read neither dirty count/span nor dirty words, and must never takeFrom/clear/restore membership. Ordinary dirty sync remains unchanged. Membership is preserved on success and failure, exactly as the existing owned-span fence (`write_work.go:334-344`) already preserves unrelated mutable borrows. The native file barrier need not decide which concurrent ordinary writes also reached disk: those writes receive no native publication authority from this fence.

Retaining RLock through extent observation matters: it excludes pager-controlled growth/truncation/Close during sync+Stat+store. Do not sync, unlock, then Stat a later extent and call that later growth durable. Do not substitute len(chunks), p.numPages or a guessed dirty maximum. The current index wrapper silently ignores Stat errors; a native path may explicitly propagate a real Stat failure under the selected stricter availability policy (ordinary behavior unchanged), or conservatively keep the old extent without claiming a larger one. After a capsule sync has actually succeeded, a later Stat failure is not proof that the capsule is undurable.

The retained token FD supplies identity/authority; operations.pager and syncPath are retained callback context/diagnostics. Native capture binds the same original DATA/PRIMARY pager and generation (`native_stable_pager_capture_v6.go:235-240,339-386`) and transfers the token into the same seal (`native_mvcc_seal_preparation_v6.go:551-555`). Never reopen the path or fall back to p.file after retirement. Physical Close can clear mappings/dirty bits and close its own handle (`physical_close_work.go:198-223`); an independently retained FD still fences the same inode's page cache. The stable-file-after-Close and path-replacement source controls document this intended identity property. A retained FD does not itself authorize publishing after DB.Close, after a stale index switch, or after external same-inode mutation: original seal/basis/closed-state validation and lifetime custody must still hold. Reopen proof must use the original recoverable root/closure, not mere readability from a still-live mapping.

## Dependency and authority order is unchanged

`executeDurableRootStorageTransactionV1` (`durable_root_runtime.go:2061-2138`) flushes/syncs external resources, materializes original candidate metadata, syncs indexes, then installs authority. `nativeAuthorityScope.syncIndexV6` (`primary_storage_operations_v6.go:38-62`) syncs the captured PRIMARY token, stabilizes its namespace, then syncs DATA. Keep both barriers. The later three-page capsule fence uses PRIMARY's physical file; it cannot substitute for DATA's earlier file barrier. Candidate images are copied before their index fences, remain immutable/owned, and the selected authority references only that captured closure. Concurrent ordinary append may persist extra bytes without changing the selected immutable logical root. Current finite Set flush/sync supports only its genuinely empty selected branch (`resource_empty_sync_work_v6.go`); file sync is not a replacement for vlog/outer-leaf/template/dictionary external dependencies or directory durability. Unsupported nonempty dependencies remain refused before effects.

On platforms where mappedRangeSyncRequired is true, file sync alone is insufficient. Refuse the native capability before activation on BOTH captured index pagers and authority path unless a true exact-page/mapping closure over every required DATA/PRIMARY candidate image is already retained and admitted. Flushing only the final capsule range does not close dependency pages. Do not retain a guessed dirty maximum, silently skip msync, or discover unsupported platform only after copying activated metadata. The runtime guard remains a defensive check, not the first capability decision.

## The native adapter must really be one attempt

`sync_page_file_linux.go:12-24` explicitly retries EINTR and falls back to file.Sync for ENOSYS/EINVAL. Calling existing syncPageFile would retain a repo-owned unbounded loop. The minimal native Linux adapter is one unix.Fdatasync on the SAME borrowed FD followed by runtime.KeepAlive(file), returning every errno, including EINTR/ENOSYS/EINVAL, without retry/fallback. The kernel/syscall duration and internal implementation are not a fixed byte-copy count; this removes only the visible repository retry loop. No bounded elapsed-time claim follows.

For the selected minimal implementation, prefer **one unix.Fstat into an admitted stack unix.Stat_t**, immediately after the successful Fdatasync, using the same raw FD captured from the original live file and retaining file lifetime with KeepAlive on every return. Return each Fstat errno without retry, os.File.Stat, fallback, or new heap-backed FileInfo. Hold the original pager lock through both calls and durableFileSize.Store(stat.Size). Price the actual raw-FD operand, Stat_t zero/write/read traffic and fixed error/extent operations before the first syscall; use actual sizeof, not an assumed platform constant. The typed capsule uses its original pager-owned live FD while holding p.mu; captured index operations use their original independently retained token FD. In each case sync and Fstat must use the same provided handle, never reopen a pathname or exchange it for another owner. A Fstat failure after a successful capsule Fdatasync does not undo authority durability: preserve mutated/ambiguous classification and original custody. This leaves kernel/libc/Go runtime internals and syscall latency outside a byte-copy/time proof, while removing repository-owned retry and opaque FileInfo construction from this native adapter.

Route BOTH native captured-index barriers AND the typed native capsule fence (`write_work.go:334`) through this once adapter. Keeping the capsule on syncPageFileFn would leave the loop in the actual final path. Ordinary syncPageFileFn, platform behavior, interruption retry and fsync fallback stay unchanged. This is an explicit native availability restriction: Linux/filesystem refusal discovered by an actual syscall is a real physical-operation error, not a manufactured budget/shape failure. Non-Linux is pre-refused unless implemented correctly. The existing retry/fallback specification must identify this scoped native exception.

Test override variables are not a production durability contract requiring native fallback. Preserve fault injection with an explicit native once-adapter seam or equivalent actual syscall control, then test its result reaches the original error owner. Existing ordinary syncPageFileFn controls must still exercise the unchanged ordinary branch. Native testFailSyncMeta in BeforePrimaryCapsuleFenceV6 remains a separate pre-fence fault guard. Arbitrary durabilitycut callbacks are currently refused by the native storage executor; do not introduce them into a fixed-work path or bypass ordinary observer cuts.

## Error phase and original custody

A native index-sync error occurs before capsule copy, so it does not make authority ambiguous. The selected stricter policy may nonetheless escalate this activated operation to sticky recovery-required while preserving the first physical error, SAME receipt/frame/candidate, token/Set/owner graph and active dispatch/lease charges. That is availability policy, not a claim it became durable or ambiguous. The current `publishWithWorkV6` unmutated branch (`root_publication_activation.go:1793-1803`) still returns retryable; it does NOT already implement that chosen sticky policy. Its explicit original error transition/notification admission is part of the coherent implementation batch.

Once the capsule copy begins, the original mutation flag is already true (`write_work.go:300-304`). Any actual fence error, EINTR or post-fence Stat/commit error then retains the existing mutated/ambiguous classification. Do not infer known failure from EINTR, retry the capsule under a new owner, or report success from an unobserved fence. All resources survive to genuine Finish or visibly incomplete sticky error custody. Error-state Close/Stop may return the original sticky error without teardown; it must not call Complete/refund or pretend physical settlement. Successful/paused-Finish Close must still genuinely join. Pre-effect work exhaustion, stale preparation, cancellation and unsupported capability remain refusal paths and never enter sticky physical-I/O poison.
