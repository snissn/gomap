## Cohort ownership and physical retention

The timed 128x operation (durable_root_bench_test.go:373+) is capture + actual selected source-kind clone/import + scoped tokens + original value read + Snapshot close + wrapper release. It is not Vacuum/GC/DB.Close latency. The off-timer retention method creates one additional loan, retains the original snapshot and descriptor scope, replaces values inline, advances two slots, vacuums to another actual DATA generation and records original file handles.

Raw files8/files16 report 262144 old DATA bytes and 1048576 old PRIMARY bytes while held. All original cohort paths remain: 8/6528 bytes and 16/13056 bytes. GC deletes zero while the reader is held, zero after last-reader finalization while the descriptor scope remains, and zero after scope completion in this immediate observation. Last-reader cleanup is a single 48791/67305 ns event, not a latency distribution. Governed bytes fall 305424->222064->162592 (8) and 432336->278832->162592 (16) from held, through reader completion, through scope completion. The common 162592 residual is not evidence that temporary borrower references remain: reader primaryOwner/treePager are explicitly checked nil and wrapper/scope edges have completed.

index_gen_db.go:34-128 sends the retired zero-reader generation to the existing ghost manager instead of physically closing immediately. pools.go:193-260 scavenges on a 1-second ticker only when age exceeds 5 seconds and pins have drained; this fixture does not force age or await that boundary. The generation retains its shared PRIMARY physical owner and recovery dependency custody (index_gen.go and primary_dependency_v5.go); valuelog.Manager's stable identity deletion lease refuses deletion while physical identity pins survive. Both recoverable slots and one-hop frontier proofs are advanced before GC, but doing so does not override original generation/descriptor ownership. Source therefore explains why prompt reader/scope disposal need not imply prompt physical reclamation. The rows do not expose per-file blocker identities, so attributing every retained vlog file solely to one specific ghost edge would exceed the evidence.

The terminal benchmark step explicitly calls actual DB.Close, which drains ghost/index owners and checks oldArena.MetadataOwner().PhysicalClosed(), owner.Bytes()==0, ExternalBytes==0 and ExternalLeases==0, then repeats Close. The raw closed-governor-bytes is zero for both sizes. It does NOT record old DATA/PRIMARY file sizes after scope or assert original vlog names absent after DB.Close. Zero governed bytes/physical owner closure must not be described as zero filesystem footprint or successful GC deletion. An eventual-reclamation requirement would need separate original-owner/blocker observations and maintained completion boundaries, not a changed target in this diagnostic.
