## Admission and observation rules

1. Each helper reserves its header/result/local traffic before the first protected load, then takes only its original short lock scope. Size actual operands and result structs, not twice the entire containing PruneCursor when the helper reads only a few embedded fields. A local stack copy is still work and is admitted. A failed Reserve returns a fixed incomplete/unsupported result without reading that operand.
2. Before each linked node, slice element, map lookup or nested entry is inspected, reserve that visit and its local arithmetic/result traffic. Reading a len/cap header is fixed work; reading all elements is not. Never count first and reserve afterwards. Map len is usable without enumerating Swiss-map backing; map capacity or exact Go-heap allocation is not invented.
3. Protected mutable traversals must complete under their original lock within one observation step. If they cannot fit the remaining Q32/1MiB, return `ObservationUnitTooLarge` with the admitted prefix count and no complete aggregate. A partial prefix is not the whole value. Do not retain a binding/map/node pointer over return, pin an observer node, hold a lock over yield, or create an enrollment to make observation progress.
4. Immutable private materialized-frame observations may use an integer ordinal and restart from the original head on the next call. Every repeated link is charged before inspection. The returned integer is not a retained pointer or authority. If the prefix to the requested ordinal no longer fits Q32, report unsupported geometry. Do not introduce a new traversal framework to support larger geometry in this batch.
5. Where a pricing operation depends only on header counts, observe those counts and evaluate its SAME pure arithmetic. Do not execute the scan merely to learn its number of visits. In particular installed-page validation V needs allocated-vector lengths and retirement/PageID lengths, not a traversal of all allocated page values for every frame. Exact equality/membership validation remains the original actual activation's responsibility.
6. Calling `AdmitRetentionResize`, `AdmitRetentionClose`, `ResizeWork`, Add, Remove, Enroll or a completion-plan admission method is not an observation. These reserve production work or may mutate original state. Derive their source cost from their original concrete size expressions or factor only a tiny pure calculator shared with the original method. No temporary scalar-precharged work or nil-work call.
7. Every product, addition, rounded charge and conversion checks overflow. Unsupported provenance/foreign lease/unknown retention shape/changed basis is a visible row, never zero. A price larger than32 is a useful returned price; observing the scalar price need not execute the priced operation.
8. No all-graph lock is added. RootReuse -> DB -> runtime and allocator -> ledger are used only as in their existing helpers; Snapshot.iteratorMu, token namespace, Set pair, pager RLock, Owner.mu and original budget.mu remain separate existing scopes. Do not take Owner.mu then call a helper that takes enrollment state.mu: the real enrollment path takes state.mu -> Owner.mu. Active enrollment details are observed under that existing order or classified unsupported, not read under an invented reverse order.

## Review finding: strongest existing header-lifetime seam

The two preactivation headers are NEW retained private storage. Once visible, activateWithWork stores the SAME DBState in db.state and publishes SAME snapshotView through snapshotViewRO; it then clears install.activationState/activationSnapshot. Their ordinary published role does not retroactively admit the private preparation lifetime. The strongest existing mechanism is `primaryarena.AdmitRootMetadataWithWorkV6(cert.Reference(), bytes, w)`, already used for primaryStateRootV5 at candidate phase4. It joins the original root bank.metadataCharge, owner, release queue and generation-tagged root lifetime. Existing `AdoptPendingRootMetadata` can transfer previously admitted pending storage at an existing legitimate ownership transition; neither creates a new owner. This is a repair candidate, not an assertion it already covers the headers. Lock-free snapshotView acquisition can transiently retain the old header before installing its reader pin; an independent Snapshot can also retain DBState. The observer cannot prove that root's last bank edge covers every such temporary header alias merely by comparing current refcounts. Independent review must settle the exact sufficient envelope/last-reader rule. Until reviewed repair/proof, show the independent rounded allocations as uncovered, keep full admitted total incomplete, and do not redesign notification/header ownership here.
