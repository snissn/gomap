Use independently charged, stable branch allocations; do not copy the exclusive private hash helper into shared authority. This is a design recommendation only, not source acceptance, implementation authority, or Q32 fit.

## Existing primitives and the reason to choose Patricia

`private_control_capacity_v6.go:10–36` explicitly excludes mutation/enumeration while a mutation is suspended. Its slots carry no values/deletion and it owns a single exclusive growth/rehash operation version. Its avalanche has expected distribution, not a worst-case probe bound. The useful reuse is checked sizeof/capacity arithmetic, SAME-owner preallocation admission, old/new overlap accounting, and detached RemovalWork debt. It is not a shared canonical map.

`generation_v1_tree.go:115–210` already demonstrates fixed-width compressed radix paths, first-differing-bit/prefix calculations and source-visible typed nodes. Its stateNode itself is not reusable: 16-way children, chunk summaries, immutable/COW page semantics and constructor/retirement contracts belong to allocator state. Copying that tree would create unnecessary COW publication and metadata-page obligations. Reuse its tested bit/prefix ideas, with small mutable typed ledger nodes and original ledger exclusion.

A shared open-addressed map can be made correct, but its smallest correct version is not the existing private set. Deletion needs explicit tombstone/backshift semantics; clustering gives worst-case O(capacity) lookup; growth needs either full rehash/copy, a shared migration continuation with mixed-table search, or stable chained subtables. A paused native operation whose proof is invalidated by ordinary writers can repeatedly restart. Stable subtables avoid whole-array relocation but require potentially history-sized table probing unless their directory is itself bounded. Fixed-width Patricia removes this growth/collision/version problem directly without selecting a new allocator, global gate, or registry.

## Concrete canonical objects and bounds

Use two distinct typed roots in ReservationLedger, replacing owners and candidates, not shadowing them. Reservation remains the canonical candidate object, with a CandidateID leaf key and parent/role fields included in its constructor charge. The page-ID index has one stable claim leaf per actually owned ID. Its value should be the original *reservation identity; an accessor exposes the SAME current CandidateID semantics under ledger.mu. This permits Supersede to rekey the same reservation without visiting every page claim. If literal copied CandidateID values are retained instead, Supersede remains per-ID work; do not claim a constant rekey.

Binary Patricia branch discriminating-bit positions strictly increase along every descent; leaf keys are fully compared. All 64 page-ID bits and 128 CandidateID bits participate. Page zero and MaxUint64 need no sentinel encodings; the existing candidate-zero rejection is a semantic rule, not an empty-tree marker. A nil root/child encodes absence.

For key width W, the source-proved structural cap is W branch visits plus one leaf comparison: **65 examined nodes for a 64-bit point query; 129 for a 128-bit point query**. An insertion uses at most two descents (find a leaf/full-key difference, then find the first larger discriminating bit), at most **2W+2 examined existing nodes**, and a fixed parent/root/two-child splice. The full-key xor/first-difference computation is one uint64 operation for owners or two fixed uint64 words for CandidateID, not a variable byte/string loop. Actual field loads/stores and key comparisons must be separately priced from these visit counts.

Deletion by a genuinely owned leaf handle reads that leaf, its parent, grandparent/root slot and sibling, then splices out leaf+parent and repairs the sibling parent. This is a constant number of distinct structural objects; reads/writes and an identity check remain actual charged work. Deletion by key pays one bounded lookup first. Do not claim direct-handle deletion when the caller stores only a uint64 ID: either lookup the key or store an admitted stable handle in the original producer. An ordered owners lower-bound query can find the first point at/after start with at most a root-to-leaf path and bounded parent/sibling descent (at most 2W branch visits plus a leaf); no owner-map whole scan is needed to find the first page point in a range.

These are structural step caps, not a selected records/bytes allowance. A whole 129-node atomic lookup does not fit Q32 merely because 128 is a fixed machine key width. To avoid ordinary-writer invalidation starvation, admit the whole chosen fixed-width operation before reading/mutating its structure under the original ledger lock; no global-version restart is needed. If a budget cannot admit that whole operation, refuse truthfully. A future requirement to make this operation itself yield below that cap needs a distinct pinned-path/handoff proof; it is not solved by saving stale peer pointers.

## Allocation and last-alias ownership

Prefer separately allocated, typed branches for the first implementation. A common intrusive pitfall is to embed a branch in the leaf that happened to allocate it: later deleting that leaf may leave its branch routing unrelated live leaves. Refunding the leaf frame then refunds a live branch. Independent branches avoid that containing-lifetime problem without a pool, second owner, or general keeper.

Each nonempty index with n leaves has exactly n-1 live branches. Charge every actual independent allocation via Q(actual sizeof type), with checked arithmetic, before allocation/effect. Candidate leaf storage is included once in Q(sizeof(reservation)); page leaf storage is Q(sizeof(pageClaim)); candidate and page branches use their actual distinct sizeof (or one typed/common routing representation if explicitly selected). The fixed two roots/control fields are included once in Q(sizeof(ReservationLedger)). For the live canonical indexes:

`C_live = Q(sizeof(ledger)) + sum Q(sizeof(reservation)) + sum Q(sizeof(pageClaim)) + sum Q(sizeof(candidateBranch)) + sum Q(sizeof(pageBranch))`.

This expression excludes the separately required reservation ID/coverage backing, original burn links/pins, pending producer objects, committed receipt aliases and scalar RemovalWork debt: each remains counted under its actual original charge, not suppressed by index size. Transiently preborn but unlinked leaves/branches are additional charged objects. There is no capacity-sized relocation or rehash overlap. Admission of even one branch can still encounter the existing Owner enrollment/binding costs; representation choice does not make those disappear.

Before insertion, stage an original candidate/claim leaf and at most one branch under that producer's existing continuation, admitted before allocation. No search pointer survives a return. Once both allocations are available, perform a fresh whole bounded check/splice under ledger.mu. If another writer won the key, return the precise existing conflict/idempotent outcome and detach/scrub/refund the unused stage via its original owner debt. Never hold the shared ledger gate across returned work refusal. A successful deletion returns the detached branch and leaf to the owning original cleanup; clear all parent/child/value/cursor aliases before refund. Parent/child pointers are structural aliases, not a second metadata owner.

Reservation lifetime is not map membership. A page leaf referring to r, a producer, a committed seal/receipt, or a pinned burn descriptor can each keep r physically/financially live after its candidate-index edge detaches. Preserve the selected explicit original-edge accounting and finish order; do not rely solely on Go reachability. Branches need no cross-return pin protocol if all traversal and splicing is done under ledger.mu and only original leaf/reservation handles escape. Original source identity checks must distinguish a newly reused CandidateID from the old committed receipt's r. Finish removes an ID only when the canonical claim leaf still refers to that exact original r, not merely when copied candidate bytes happen to match.

Supersede must first validate old and next under the same lock and admit all required lookup/rekey effects. Then detach old key, update the original reservation's key/current ID and reinsert without a fallible gap; reuse the detached structural branch where applicable or preadmit any needed branch. Existing page leaves refer to r and therefore keep owner semantics coherent. An r leaf key may not be mutated while it is still linked in the CandidateID tree. Preserve all supported source states and genuine retry/failure custody; this is not permission to weaken Supersede validation.

## Connected edits and limits that must remain named

`generation_v1_reservation.go` contains direct lookup, insert, delete, Supersede, release/Fail/Publish, and three whole-range consumers. Switch every canonical ordinary/native access together. `generation_v1_metadata_claim_work.go`, metadata reuse/work, allocator preparation, append, rollback and allocator publication validation currently account map count/probes/scans through legacy formulas; adapt them to actual fixed-width lookups, node birth/splice and original per-ID progress. Update snapshot/profile/envelope consumers and constructor/shutdown custody. No map snapshot may be left as a second authority. Tests using literal ledger fields must adopt the typed canonical operations rather than retain test-only old maps.

The two map replacements **do not** bound all ledger operations. `reservedLocked`/`reservedByOtherLocked` still inspect every pending candidate tail and burned range. `firstConflictingRangeLocked` scans owner points and all pending/burn intervals. CandidateID ordering does not answer spatial tail queries. Use the owner tree's ordered point query for owners; pending/burn intervals still need the already selected pinned original descriptor traversal with saved progress/stop identity and actual per-node admission, or a separately selected spatial augmentation. That traversal can be history-proportional in total while every persistent-progress step is bounded; do not call a whole range reservation constant. Pure point-map closure and original reservation/coverage enumeration are distinct obligations.

The pinned descriptor list already starts before the first burnable write and includes nonburned original tails, so it is the natural existing representation for pending/burn exclusions. It must cover every actual tail-producing caller, including paths that previously only appeared in candidates enumeration. Reservations with no tail still own their indexed page claims. Range traversal under ordinary concurrency needs its own stop/correctness semantics; the map decision does not authorize ignoring newly conflicting reservations or detached receipt exclusions.

### Spatial prerequisite; not part of this two-map selection

The current producers do not promise strict disjointness between a candidate's own point claims and its own metadata interval. `reserveTailLockedV1` checks fresh data IDs against other owners, finds a tail against the already linked exclusions, and only then inserts those fresh IDs and the tail (`generation_v1_reservation.go:386–475`). Thus a fresh data ID equal to a chosen tail page is accepted as the SAME candidate's two roles when the caller supplies such operands. `claimDataLockedV6` likewise checks `reservedByOtherLocked` before adding points (`allocator_preparation_work_v6.go:577–605`). In contrast, `claimReusedMetadataLocked` explicitly rejects even its own supplied data inside its metadata interval (`generation_v1_metadata_reuse.go:139–185`). A spatial replacement must preserve these distinct producer contracts, not silently reject same-candidate duplicates or count them as one reservation role.

The inspected normal claim producers exclude other candidates under the SAME ledger mutex. Supersede changes the original reservation identity/key atomically and does not create a new spatial extent; Fail/Rollback preserve the original written tail as burned exclusion. These checks support investigating one spatial exclusion index whose payloads are the original point claims and original pending/burn descriptors, replacing owner point membership plus interval membership rather than adding a third shadow authority. They do not by themselves establish a complete implementation: it must distinguish point/interval roles at equal starts, preserve allowed same-candidate overlap, exact object identity across retarget and pending-to-burn transitions, overflow-safe interval semantics, and source-visible summary update and deletion costs. Existing reservation counts count roles, not a disjoint spatial union. No spatial-index bound or retained-lifetime proof is accepted here.

For this consultation the smallest selection remains the two canonical point indexes. The original range/placement/coverage loops remain explicitly open and charged through the connected descriptor protocol; a CandidateID index cannot make their spatial traversal constant. This recommendation does not require or implicitly authorize the broader spatial replacement.

Minimum connected controls: independent high-cardinality 64/128-bit adversarial prefixes; keys0/Max and candidate-zero semantic rejection; delete root/only leaf/internal sibling and arbitrary allocation-order branch ownership; Supersede with many claims and same-ID reuse while old Finish remains live; effect-free short work/admission at each stage with ordinary inserts/deletes between returns; exact charged leaf/branch endpoints and delayed original-r aliases; ordinary nil-work versus native finite shared storage; and selected real reservation/commit/pinned-burn Finish/cancel/shutdown controls. These are discriminating obligations, not an execution grant or a request for a new generic framework.

**Smallest defensible batch:** two typed fixed-width indexes, stable original leaf objects and independent branches, complete constructor/cleanup/admission and all canonical access adapters, plus the already preferred original pinned-descriptor commit/Finish protocol. Keep range-enumeration, existing Owner growth and whole-Q32 closure explicitly separate. No new global owner/registry, arbitrary capacity or history-based scalar precharge is selected.
