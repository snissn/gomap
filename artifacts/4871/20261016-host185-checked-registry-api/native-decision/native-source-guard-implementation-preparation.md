## Proposed core contract

A source guard is a distinguished positive leaf in the SAME `ReaderRegistry` slow Patricia tree, not a second collection. Add immutable floor and counted source/birth ownership to that canonical leaf; ordinary reader IDs must not accidentally consume guard membership. A guard reference is opaque and identifies registry, exact original DATA generation/pager and immutable leaf identity. An original role owns one counted reference; a partially born child owns another. Repeated transfers move that reference, rather than registering again. Checked retain rejects overflow/stale/wrong-generation authority before effects. No branch lifetime is folded into a leaf that can disappear first.

Use the positive tree deliberately. Minimum observation holds `registry.mu`; slow guard removal also holds it. Therefore a newly registered fast reader omitted by a concurrent sixteen-cell scan is still covered by its overlapping immutable slow guard, or registered before that guard could be withdrawn. A guard in a recyclable fast cohort does not provide this argument. Keep the existing fast reader representation and public ordinary growable API.

Proposed conceptual operations (names can follow local conventions): prepare an unpublished guard with ordinary/finite explicit origin; retain a known original guard under its existing source exclusion; transfer a reference into a child; release/detach with ordinary or work-bearing completion. Native leaf creation and all retained/control allocation must use the SAME registry metadata owner, with admission outside `registry.mu`, revalidation before insertion, and original partial-preparation custody on failure. No Owner callback under registry/coordinator publication locks. Last release first ends tree/role aliases, then transfers accounting by value to the original parent's admitted removal receipt. Ordinary cleanup uses the C1 header receipt. A leaf cannot drive its own containing refund.

A reference may be stored inline in an already admitted original Snapshot, root preparation, member/seal, runtime slot, directory lease or build group. Price the actual enlarged containing allocation once. Current `DBState`/`snapshotView` copies remain ordinary published GC outputs; do not give naked copied headers responsibility for new private guard lifetime. Their current-role handle can live in the original generation/publication holder and be acquired under `rootReuseMu`. No per-header exemption or extra keeper is needed.

A new guard's floor is the actual DATA reuse floor. For PRIMARY that includes `primaryStateRootV5.dataCommit` and the selected runtime's four `dataFloor` entries, not the PRIMARY commit sequence or MVCC version timestamp. A guard borrowed from an ancestor is valid only if its immutable floor is <= the new source's required floor. This permits safe partial handoff, but an indefinitely retained ancestor must not be presented as successful reclamation: fresh accepted sources should obtain their own exact-floor guard before releasing the ancestor once their construction permits it.

The first implementation decision is the native positive-guard constructor, not another minimum algorithm. `RegisterWithHint:197–240` performs ordinary speculative Owner admission; `Begin/StepNativeMVCCRegistration:25–95` is fast-only. No native last-drop lifecycle is closed by the present helper. There is no safe source-only claim that yielding halfway through its current mutation preserves exact summaries or lets concurrent insert/remove resume without stale ancestor aliases. A new mutation protocol must explicitly retain any unfinished original nodes and permit conservative lower summaries while repair is incomplete, reconcile concurrent changes without unlimited restart, and finish accounting at the SAME original parent before its refund. Whether to extend the original registry header with a typed repair continuation or stage a source-supported bounded commit is a concrete follow-on source decision, not an implementation detail this advice licenses. Two connected obligations cannot be hidden by inheritance: (a) keeping one oldest ancestral guard forever is safe but may prevent useful reuse; exact-floor guard refresh and its failure custody are required for reclamation, and (b) the generation wrapper still must outlive all guard/birth aliases even if no ordinary Snapshot was returned. Guard APIs must reject cross-generation/registry use before mutation. Recovery's first roots must be guarded before reuse can begin; missing/malformed floor refuses initialization rather than fabricating zero authority.
