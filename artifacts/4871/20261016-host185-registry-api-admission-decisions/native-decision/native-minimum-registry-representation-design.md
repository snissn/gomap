# SAME ReaderRegistry fallback representation decision

Decision: select one typed, augmented positive-handle Patricia tree inside the original ReaderRegistry, retaining its sixteen existing fast sequence cohorts. Replace `seqs`, `free`, `min` and `dirty`; do not add an observer registry, separate owner, persistent minimum cache detached from live registrations, or global aggregate. This is a source-grounded design recommendation, not implementation/source acceptance or a Q32 fit claim.

## What must change and what remains separate

Current registry.go:63–108 grows/recycles two vectors; :162–180 can append to `free` on unregister; :183–245 scans historical `len(seqs)` when dirty. registry_unregister_work_v6.go:15–37 therefore refuses a positive-handle last release when the free vector needs growth. A previously large, now mostly empty registry retains scan/shrink costs. NativeMinimumGeometry currently correctly counts historical slots, not live readers; substituting live count in that formula would be wrong.

Keep the common zero-allocation same-sequence fast join and sixteen fixed shards. A coherent combined query under registry.mu reads the sixteen cohorts and the slow-tree root summary. It never walks slow registrations, traverses a retired vector, or leaves a dirty repair for the last unregister. This closes representation cost due to historical fallback cardinality. It does not implement the producer-handoff guards from the preceding report: continuing-writer safety still requires the already specified role-complete source guard invariant. A query from the new representation can be coherent without an epoch restart, but its historical observation is not automatically safe against an unguarded later lowering producer.

## One canonical fallback tree

Use positive int64 handles as opaque keys, with W=63 significant bits. Each live fallback registration has an independently allocated typed leaf containing handle, full uint64 sequence, parent link and its exact original admission charge. Each independently allocated typed branch has discriminator, two child links, parent link and cached subtree `{minimumSequence, minimumHandle, maximumHandle, liveCount}`. Node tags must be explicit; do not use unsafe encoded pointers. All slow-tree nodes and summaries are protected by the original registry.mu; no path/node pointer survives a returned yield. No exported node views or pooled retained arrays.

An n-leaf tree has n-1 branches. Each insertion allocates one leaf and, except into an empty tree, one branch. A delete detaches the leaf and its one now-redundant parent, then repairs ancestors. Compressed discriminator indices strictly increase: at most 63 branch visits and one terminal leaf per descent. Store distinct branches separately from leaves; coallocation must not make a deleted registration's charge disappear while a surviving branch remains an alias into it. Duplicate sequences remain independent positive handles, as today; their cached minimum naturally persists until the last such registration ends. Sequence zero and MaxUint64 are both representable, since absence uses node tags rather than a sequence sentinel. Saturated fast cohort counts still fall back; they must not overflow or turn ordinary registration into the fast-only native policy.

Handle reuse must itself be bounded and release history. Do not use a monotonically exhausting counter plus ever-retained free-ID vector. The above min/max/count summaries can select the smallest unused positive handle: if root.minimumHandle>1 choose 1; otherwise find the first internal hole, descending only one child at each branch. A subtree is dense exactly when `count == maximumHandle-minimumHandle+1`. If left is sparse descend left; otherwise use a gap between left.maximumHandle and right.minimumHandle; otherwise descend the sparse right child. If the entire root is dense use maximumHandle+1, checked against MaxInt64. This needs at most W branch visits. Counts and range arithmetic use checked uint64 values bounded by MaxInt64, before any int/int64 cast. Full positive-handle-space exhaustion is a real capacity failure, not a wrapped/reused live handle. The existing API already reuses handles, so duplicate/stale unregister is not given a new generation-safety guarantee; a live handle must be consumed exactly once.

Insertion has at most three bounded descents (find hole, search, locate splice) plus a <=W ancestor repair, one leaf init and at most one branch init. Deletion has <=W search plus <=W repair, constant splice/scrub of two detached allocations. A parent-link delete by an internal known leaf can omit search, but keeping public int64 handles requires the bounded lookup. No rotations, whole rehash, copying all entries, or history-dependent compaction. These are conservative visit bounds, not proposed work records: each actual key/discriminator/link/summary load and summary write needs its source-shaped Reserve row before access; repeated entry and any retry prefix are charged again. Bounded stack/path scratch must be included in traffic even if it does not escape.

## Coherence and fast-path races

Preserve the actual first-publication rule in registry.go:73–95 and :298 onward: claiming count 0 -> initializing -1 -> published positive occurs under the SAME registry.mu used by the minimum query. The query reads sequence before count. Same-sequence joins may remain outside mu: they cannot lower an already published cohort's sequence. Preserve post-CAS sequence validation and rollback, saturation checks and initializing-sentinel behavior; do not introduce last-fast-removal tree updates or a counter-to-tree transition.

Fast last unregister only decrements its original count. During a locked query, no first claimant can recycle that shard to a lower sequence; a concurrent final decrement can make the observed minimum conservatively low. A later same-sequence join uses the current positive cohort; a claimant of an empty cohort must acquire mu. For slow nodes, insertion/deletion and root-summary repair are a single locked, fully admitted mutation, so a query cannot see new membership with old summaries or a removed minimum still cached indefinitely. Sequence migration is unregister+new register with the required existing producer overlap, never in-place key/sequence mutation.

A fixed-height tree is a bound on source visits, not a bound on wall-clock lock waiting. Existing optimistic tryJoinFast has an unbounded CAS loop under contention; preserve its ordinary behavior only with an explicit non-claim of worst-case per-call work, or change the bounded/native attempt to one charged CAS attempt per persistent probe step. Native Step already charges each attempt and preserves its index. None of these rules prove starvation freedom under unlimited competing acquisitions; the native guarded-minimum argument avoids epoch churn, not arbitrary mutex/CAS adversaries.

## Original owner, birth, alias and refund domains

The DB generation's original metadata owner is the appropriate owner for the registry representation. It is NOT inferred from a PRIMARY arena, Set, or native caller owner. index_gen.go:84–106 separately allocates ReaderRegistry inside newIndexGen, while newIndexGenWithMetadata currently admits only Q(sizeof(indexGen)). A new owned constructor must admit the separate Q(sizeof(ReaderRegistry)) including the sixteen shards, owner/charge/control fields and tree root before allocating/exposing it. Add that constructor charge to the original generation's terminal accounting, with checked arithmetic and constructor failure unwind. Do not silently label the separately allocated registry header as covered by indexGen's containing size.

For new nodes, charge distinct allocations separately: insertion peak = Q(sizeof(slowLeaf)) + [nonempty] Q(sizeof(slowBranch)); exact sizes come from the actual final types. Maintain an exact producer total for root/leaf/branch storage; do not sum raw member sizes and round once. No history-sized backing is retained. Pending speculative nodes are born only after original Owner admission succeeds; source failure before allocation leaves registration/minimum unchanged. Reserve constructors and all actual discovery/repair traffic before the first membership effect. Under registry.mu the topology cannot change; run original Owner.AddPending/AddPendingWithWork under the established registry -> metadata Owner -> budget order, with no callback reentry into the registry. Audit concrete lease callbacks and producer lock order before implementing this nested admission. A shortage must leave the old registration and custody unchanged; allocation failure does not yield a usable handle.

The fixed header dies only after physical generation completion AND the last original wrapper/capture alias and any cleanup debt. index_gen.go:248–343 already waits for physicalCompleted, zero wrapper borrows, no startup owner and no close error, then clears registry/pager/allocator aliases and transfers by-value metadata completion. Extend that exact terminal accounting and verify all registry call scopes retain their existing generation/discovery exclusion through return. Do not refund the registry header at the last reader unregister or at physical pager Close alone. No public DB registry accessor exists; lifecycle.NewReaderRegistry itself returns a standalone exported object, so retain a documented standalone legacy GC constructor for non-DB use rather than assign an unrelated owner. Tests constructing naked generations need explicit owned-vs-legacy setup. A new externally borrowed registry API would require an original generation borrow, not rely on Go liveness alone.

## Native last unregister: use the existing completion

NativeMVCCRegistration is currently fast-only (native_mvcc_registry.go): its embedded state saves registry/sequence/hint/index/phase/id; exhaustion returns id=0 and Snapshot refuses, rather than allocating a fallback. Keep that support boundary. Its successful id remains owned by the registration until finalizer Cancel, including the interval where final Snapshot adoption refuses. Cancel must reserve before decrement, clear the embedded registry/handle aliases only after consumption, and never double-drop Snapshot.registryID. No tree allocation is needed for this native partial-registration/cancel path.

The important native positive-handle path is dataDependencyLeaseV6.releaseCurrentWithWorkV6 at native_mvcc_data_dependency_release_v6.go:108–145. Change its unregister child to return an accounting-only completion for detached tree allocations. Under registry.mu fully admit lookup+splice+all summary repairs, clear every detached leaf/branch alias, copy owner/charge only, then return. Do not run a synchronous Owner.Remove inside unregister. The provider must consume the handle only once and preserve the completion across subsequent refusals. It adds the charge, with checked arithmetic and owner equality, to its existing DependencyDirectoryReleaseCompletionV6 after clearing its registry/generation aliases.

In this exact DATA route, owner equality is SOURCE-PROVED: :34 chooses metadata := idx.metadata; :44 stores it in lease.metadata; :48 passes the SAME metadata into NewOwnedWorkDependencyDirectoryV6; dependency_directory_release_work.go:60–64 forwards it unchanged to the directory. Registry construction must bind that SAME idx.metadata. Existing generation completion at :92–94 already checks its metadata against lease.metadata. Add an equivalent check for detached registry storage; do not infer equality from kinds or matching sizes. A PRIMARY-owned provider or any different-owner route cannot add these charges to its single-owner completion. Such a route requires an explicit second owner/charge and original RemovalWork in the SAME existing receipt, or is unsupported until that original receipt is extended; do not substitute owners.

DependencyDirectoryReleaseWork already provides the needed custody: it saves provider completion at :186, binds producerRefund at :213–220, clears provider/directory aliases at :232–246 and only then consumes the exact original Owner RemovalWork at :250–259. This avoids a new registry disposal queue, node keeper or ownership domain. Ordinary unregister synchronously drives the same detached-charge completion after returning through its actual node teardown; finite native callers use the original surviving parent. Unsupported lease capability and real cleanup failure stay visible with the SAME owner/amount/cause; do not clear or refund pending debt on error.

The metadata owner's B bindings are a separate real cost. Owner.AddPendingWithWork scans/admit-forwards/admit-rollbacks every binding (owner_growth_work.go:13–52). Owner.RemovalWork is resumable and can revisit bindings/restart during disposal (owner_work.go:68–187). Tree height does not make those operations constant or Q32-sized. Preserve their concrete capability checks, saved cursors and exact accounting on refusal. The selected completion route bounds the membership-removal unit independently of historical fallback size; full physical/accounting retirement still depends on actual Owner traffic and continuing enrollment. Do not replace that with atomic whole-owner removal unless its entire B-dependent unit is proven/admitted; the maintained atomic helper explicitly has B(B+1) conservative visits and is not a history-independent solution.

## Connected edit and control map

1. lifecycle/registry.go: typed fallback nodes/summaries, owned constructor, bounded gap selection, coherent min, fallible registration and ordinary deletion completion. registry_unregister_work_v6.go: bounded positive-handle mutation and accounting-only result, no free-vector append. 4. Generation retire/ghost minimum queries remain coherent and bounded by 16+root summary, but their external generation-list traversal is not closed by this change.

Discriminating focused controls: >16 distinct cohorts plus many historical registrations then full drain; min at every deletion order; duplicate uint64 sequences including 0/MaxUint64; forced fast saturation; arbitrary unregister order/unknown handles without stale-handle guarantees; reuse smallest holes after deleting low/interior/high handles; dense/gapped and maximum-positive-ID boundary using factored pure summary validation; independent brute-force model versus summaries; height/link/count invariants. Zero-work/capacity/callback refusal at every new allocation/splice boundary must leave membership/custody unchanged. Verify peak leaf+branch admission, constructor partial unwind, no allocation at deletion, detached charge survives parent refusal and refunds once after alias scrub. Existing original first-claim/min-scan and native partial-registration/cancel controls stay; add fast last-decrement/reclaim/query interleavings, concurrent lower first claim, duplicate cohort joins and cancel before/after Snapshot adoption refusal. Test original DATA provider with a genuine positive fallback handle, SAME-owner successful receipt and an intentionally different-owner refusal. Header accounting must persist through DB physical Close with a held Snapshot/DATA-directory borrow, then clear on actual final completion; failed close retains it. No timing/benchmark run is proposed by this advice.

## Disposition

Selected representation is sufficient for a fixed-key-width coherent membership minimum and fallback logical deletion without historical vector work. First implementation prerequisite is the fallible owned-registry birth/registration and original completion plumbing; it cannot be bolted beneath the current infallible-looking Register API while swallowing admission failure. Owner fan-out/lease capabilities, producer-handoff roles, ordinary allocation/retention performance, and lock/CAS progress require their own explicit source/evidence dispositions. No source implementation, numeric allowance, genuine publication, continuing-writer qualification or Q32 success is accepted here.
