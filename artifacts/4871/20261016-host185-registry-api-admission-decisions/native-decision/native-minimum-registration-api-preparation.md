## The resource policy requires a real API change

Existing ordinary `RegisterWithHint` can grow GC fallback storage. Adding mandatory admission against the original generation metadata owner introduces genuine capacity or closed-binding failures. It cannot preserve every former unlimited-GC capture success while also obeying that finite owner. Occupying all 16 fast slots is **not** such a resource failure: ordinary captures must retain growable fallback, and succeed when its actual admission succeeds. Explicit bounded/native fast-only policies remain separate.

Backend `db.DB.AcquireSnapshot` currently returns only `*Snapshot` (`db.go:1688`). Its bool capture core (`1768`) cannot report a new resource failure precisely. Public `TreeDB.DB.AcquireSnapshot` (`public.go:2507`) and caching capture similarly return pointers/interfaces only. There is no established error-only Snapshot result, nil error channel, or compatible no-error wrapper for this newly fallible operation. Retaining the old wrapper by returning nil, inventing `ErrClosed`, panicking, or indefinitely retrying would change failure semantics while hiding the cause. An additive checked API alone leaves these actual ordinary callers unresolved.

Root has selected the coherent breaking migration: backend and caching `AcquireSnapshot() (*Snapshot,error)` and public `AcquireSnapshot() (Snapshot,error)`, with actual resource error propagation. Root `AGENTS.md:10` explicitly permits pre-alpha public API changes without backward compatibility guarantees. Preserve existing successful capture modes, not an impossible promise of unlimited future capacity. A genuine nil/closed DB still returns its existing closed error; a capacity/closed-binding failure must retain its actual cause. A capture error must not become an empty result, missing key, missing version/floor, typed retry, or successful unpinned Snapshot.

Migrate the internal bool capture core to return error. `api.go:160` and `pools.go:45` currently collapse capture failure to `ErrClosed`; they must pass through the cause. The same applies to stable snapshot acquisition (`db.go:2144,2164`), recoverable-root capture (`recoverable_root_set.go:723–740`), locked helpers, and ordinary branches of the existing error-returning bounded capture (`db.go:2033`). Do not replace ordinary capture with `AcquireSnapshotWithAllocationAdmission`: its documented fixed-registry policy intentionally supports only 16 distinct cohorts and omits ordinary growable leaf-pin behavior.

## Outside-registry maximum admission, not a nested callback protocol

Use the prior selected handle-tree representation: each slow insertion requires at most one separately admitted leaf and one branch; it never needs a history-sized rehash. Root has selected preadmission of that maximum **outside** `ReaderRegistry.mu`:

1. Keep the existing atomic common-cohort join. Under `registry.mu`, first-shard initialization remains serialized; check whether a slow insertion actually needs storage.
2. If needed, leave `registry.mu` and admit the checked rounded maximum leaf+branch against the exact generation metadata Owner before allocation. Keep the original rootReuse/generation capture custody throughout this attempt and its cleanup. No bare exported registry pointer substitutes for that custody.
3. Reacquire `registry.mu`, recheck fast cohorts and the actual current tree. A concurrent join/insert/removal may change what is needed; the maximum remains sufficient. Adopt only the nodes actually spliced, with exact charge transfer and no duplicate registration. There is no global-version restart requirement and no authority permit surviving this synchronous attempt.
4. Detach/scrub unused speculative nodes and aliases before their exact pending refund, after unlocking the registry. Count **the full actual speculative peak**, including any existing tree plus both speculative objects, original attempt/control storage and any retained cleanup state. Existing Owner admission is before heap creation, not a retrospective sizeof estimate.

A successful method cannot leave an unowned speculative charge/debt. If unused-node removal/refund cannot complete, original attempt/capture custody must retain its owner/charge and any required accounting-only continuation, and preserve the first error. If a registration was already installed, either its complete original parent adopts that pending cleanup explicitly or the failed attempt removes it through the same real cleanup path before returning failure. No “complete” flag substitutes for settlement; no node/parent alias may survive a refund. The original synchronous attempt may carry fields/embedded RemovalWork, but its own storage must be admitted if newly allocated. This is an implementation obligation, not a selected new keeper registry or a hidden GC refund. Current `Owner.RemovePending` (`owner.go:150`) panics on refused removal; blindly calling it and treating that panic/error as harmless is not the required new checked cleanup behavior.

For Snapshot capture, arrange fallible registry admission before later dependent acquisitions where the original lock/custody permits; otherwise use the original initialized Snapshot/failed-capture chain for exact partial cleanup. Current ordinary capture acquires value-log resources before registration, so changing only the Register line is insufficient. Preserve Manager/Set and PRIMARY/leaf/index borrows, the original epoch/in-flight exit ordering, private one-shot behavior, and genuine failure custody. Never return a successful partially registered Snapshot or return an unsettled wrapper to the pool. Recoverable/build/writer constructors need their existing parent-specific unwind rather than Snapshot-specific shortcuts.

## Owner, constructor and final-alias domains

`index_gen.go:84` independently allocates the ReaderRegistry containing its 16 shards. `newIndexGenWithMetadata` (`100–108`) currently admits only rounded `sizeof(indexGen)`. An owned registry constructor must admit its own header before creation, return an error, and attach that charge to the **original generation** owner/receipt. Startup (`original_startup_generation.go:19`) and vacuum replacement (`vacuum_online.go:585`) use the DB identity-registry metadata owner; their error-return paths can propagate constructor failure.

The offline PRIMARY scope is an important exception (`primary_offline_pair_v6.go:34–45`): it invokes `newIndexGen` directly; `idx.metadata` is nil, while its admitted controls belong to `stableNamespaceMetadata` and its existing parent completion. Explicitly cover any real registry allocation there with that original owner/receipt, or avoid an actually unused registry only with a proven path predicate. Do not assign its charge to another owner's lease merely because the fields look similar. Standalone unowned registry test constructors can remain an explicit GC test domain; that is not an escape hatch for production owned generations.

Header refund waits for the original generation physical completion **and** all wrapper borrows/startup aliases to end with no retained failure (`index_gen.go:248–343`). A last reader is not sufficient. Ordinary tree-node unregister detaches/scrubs under registry exclusion, then refunds to that same generation owner outside the lock. Native DATA-directory last-unregister has a proven same-owner route (`native_mvcc_data_dependency_release_v6.go:34–48`): carry accounting-only node debt through the original dependency completion and RemovalWork after aliases end. Do not mix it with the PRIMARY owner. Different-owner completion would require an explicitly represented second owner/charge in the original receipt; it is not implicitly supported by summing bytes.

## Lock proof and required discriminating controls

The concrete maintained path is Owner.mu → COWBudget.mu. `Owner.AddPending` may resize all enrolled bindings, including forward/rollback traffic. COW lease resize/acquire/close hold budget.mu only and do not invoke a ReaderRegistry callback; generation callbacks run after unlocking budget.mu (`cow_budget.go:283–311`). Native owned capture admission returns before registry registration, retaining original pending handles but not these mutexes.

However `Budget`/`Lease` interfaces permit other implementations, and admission callbacks can enroll owners. The current Snapshot callback contract forbids synchronous publish/refresh/Close of that DB, not every registry-minimum query. Holding `registry.mu` through Owner.Add could introduce registry.mu → Owner.mu → arbitrary Resize → registry.mu deadlock. Outside-registry speculative admission avoids that new edge without inventing a broader callback restriction. It does **not** prove arbitrary callback reentry under the already existing publication/rootReuse/db locks is safe; preserve their original contract. Lock/CAS contention and Owner binding fan-out remain explicit work/cost concerns, not a Q32 fit proof.

Follow-on controls should discriminate: 17+ distinct ordinary cohorts plus duplicates in cached/backend and COW on/off modes; real header/node capacity and closed binding errors through the checked public interfaces; native fast-only refusal/partial cancel; concurrent first-shard claim and speculative recheck; exact full peak/unused branch refund and retained removal failure; last wrapper delayed header refund and offline owner separation; and an admission callback that queries registry minimum without new registry-lock reentry. No such new code or controls were executed here. Role-guard producer integration is a separate selected prerequisite and must use these checked APIs if it can allocate; this report does not implement it.

There is no remaining policy-choice request: root selected checked signatures and outside-lock maximum preadmission. The outstanding work is implementing and verifying the concrete propagation/cleanup/constructor obligations above.
