## Cleanup custody is pending, not missing

`resource_original_cleanup.go:106` allocates the charged resourcePinnedBacking, stores refs1/owner/registry and increments originalCleanupEdges. custodyCompleted starts false by normal zero initialization. It is a preborn failure-custody edge, not a construction-complete flag. Constructor OperationsPhase3 plus nonzero CustodyCharge and matching owner/registry demonstrate the expected pending object in this run.

The observer at `primary_empty_candidate_work_v6.go:332` returns custodyCompleted.Load verbatim; false also occurs for a nil custody, so interpreting this boolean alone as missing custody is invalid. Here the nonzero charge and true owner/registry comparisons disambiguate it. A stronger scalar observation can explicitly report custody presence and refs if needed, but cannot demand completed=true at prebuilder phase13.

Actual native last release (`db/native_stable_pager_capture_v6.go:83` ReleaseWithWorkV6) first consumes the original operations ref once, detaches the Snapshot completion callback, finishes the SAME Snapshot close and counter, releases the actual physical owner, then calls originalCustody.CompleteWithWorkV6 in releasePhase3. That method sets custodyCompleted, decrements originalCleanupEdges and returns an accounting-only completion. The capture detaches originalCustody before draining its existing RemovalWork; only later does it scrub pager/path/native/frame aliases and return the real remaining charge. Before physical Finish/cancel this completion must not already be consumed. Ordinary success/failure similarly calls OriginalCleanupCustody.Complete only at original disposal, preserving sticky failure payload on error.

This source trace rules out the claimed failure mechanism 'construction forgot to complete custody'. It does not qualify the unexecuted actual native physical Finish or prove that no later custody defect exists.
