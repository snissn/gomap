## Confirmed repeated traversal

`ValueLogRewriteOnline` documents bounded commit batches and defaults to 256 pointer swaps ([options](/private/tmp/gomap-qs-5005-verify/TreeDB/db/vlog_rewrite.go:188), [default](/private/tmp/gomap-qs-5005-verify/TreeDB/db/vlog_rewrite.go:374)). The rewrite iterates each maintenance root using pointer projection, selects source-backed pointers, and flushes after `batchSize` candidates ([scan](/private/tmp/gomap-qs-5005-verify/TreeDB/db/vlog_rewrite.go:1938)). A flush orders candidates, reads each old value with `Manager.ReadUnsafeTo`, appends rewritten values, flushes/syncs the writer, registers created segments, and applies pointer swaps to that root ([flush](/private/tmp/gomap-qs-5005-verify/TreeDB/db/vlog_rewrite.go:1821)). Registering segments avoids filesystem refresh scans; it does **not** avoid candidate reachability scans.

All swap targets dispatch through user, system, or collection publication ([dispatcher](/private/tmp/gomap-qs-5005-verify/TreeDB/db/vlog_rewrite.go:2461)). The decisive gate is `canTrackRewriteValueLogRefDelta`: tracking requires a current tracker **and** `!outerLeavesInValueLog` ([gate](/private/tmp/gomap-qs-5005-verify/TreeDB/db/vlog_rewrite.go:2700)). User optimistic/serialized paths use the global outer-leaf setting ([optimistic](/private/tmp/gomap-qs-5005-verify/TreeDB/db/vlog_rewrite.go:2801), [serialized](/private/tmp/gomap-qs-5005-verify/TreeDB/db/vlog_rewrite.go:2941)); system and collection paths use their resolved root policy ([system](/private/tmp/gomap-qs-5005-verify/TreeDB/db/vlog_rewrite.go:2506), [collection](/private/tmp/gomap-qs-5005-verify/TreeDB/db/vlog_rewrite.go:2597)). Therefore, an outer-leaf rewrite batch passes no logical reference delta into finalization even if the tracker was repaired by the preceding scan. Empty/no-longer-matching batches can return without publishing. Optimistic conflicts can retry; collection aliases add descriptor work.

Every successful nonempty publication uses candidate resource capture: the direct path calls `captureDurableRootResourcesV1` ([direct](/private/tmp/gomap-qs-5005-verify/TreeDB/db/db.go:3462)); the activated/queued path clones visible predecessor resources and calls the same underlying closure builder ([queued](/private/tmp/gomap-qs-5005-verify/TreeDB/db/root_publication_activation.go:766)). The outer-leaf reuse planner declines a nil delta ([decline](/private/tmp/gomap-qs-5005-verify/TreeDB/db/durable_root_runtime.go:683)). Fresh capture consequently falls back to an exact scan ([fresh capture](/private/tmp/gomap-qs-5005-verify/TreeDB/db/durable_root_runtime.go:995), [projection fallback](/private/tmp/gomap-qs-5005-verify/TreeDB/db/durable_root_runtime.go:639)). Global outer-leaf mode independently disables simple logical-only projection at line 291. With no outer leaves and a valid tracker/delta, that projection may succeed; it is not correct to claim all rewrite configurations scan every batch.

One exact candidate scan performs:

1. A raw outer-leaf-reference walk of primary user/system roots, followed by a logical pointer-count reachability scan of those roots.
2. Discovery of collection/vector roots, then another raw-reference walk and another logical pointer-count scan of the discovered roots.
3. A final general reachability scan that also supplies exact counts to repair the visible reference tracker.

These calls are explicit at [candidate scanner](/private/tmp/gomap-qs-5005-verify/TreeDB/db/durable_root_runtime.go:520), including logical scans at 528, 542, and 545. Raw walks need pager nodes, not outer-leaf payloads. Logical scans dereference outer leaves to inspect their embedded ValuePtrs ([outer-leaf data](/private/tmp/gomap-qs-5005-verify/TreeDB/db/maintenance_reachability.go:319)). Each call constructs a fresh page memo; sharing/deduplication is within that call, not across the three calls or subsequent rewrite batches ([memo allocation](/private/tmp/gomap-qs-5005-verify/TreeDB/db/maintenance_reachability.go:206)). It visits the whole reachable tree rather than only changed leaves.

Thus, with N reachable entries and M successfully rewritten pointers, the confirmed path has traversal work approximately `O(N * ceil(M / B))`, B=256 by default, in addition to copying/apply work. It is quadratic-shaped when M scales with N. This is a source-derived scaling mechanism, **not** proof that it dominates the current process. `collectRewriteSwapPointerMatches` uses an iterator between selected swap keys, not an unconditional full-tree scan ([matching](/private/tmp/gomap-qs-5005-verify/TreeDB/db/vlog_rewrite.go:2992)); sparse batches can still span many intervening entries.

## Frame reads, decode, checksums, and allocation

Repeated full scans can amplify CPU and reads even with an OS-warm filesystem. Checksum-disabled maintenance uses an outer-leaf batch reader and decodes grouped records once per local batch, deliberately avoiding retention of every frame in the shared point-read cache ([batch gate](/private/tmp/gomap-qs-5005-verify/TreeDB/db/maintenance_reachability.go:216), [reader](/private/tmp/gomap-qs-5005-verify/TreeDB/db/value_reader.go:126), [grouped read contract](/private/tmp/gomap-qs-5005-verify/TreeDB/internal/valuelog/read_grouped_batch.go:39)). This amortizes subvalue decoding within a pass; it does not retain scan-wide evidence for the next publication. The existing test explicitly requires no grouped point-cache pollution ([test](/private/tmp/gomap-qs-5005-verify/TreeDB/db/maintenance_reachability_test.go:319)). Leaf-page cache hits can still help, depending on configured capacity and reuse distance.

Checksum-enabled scans use per-leaf reads with verification state ([leaf read](/private/tmp/gomap-qs-5005-verify/TreeDB/db/value_reader.go:101)). In `File.ReadUnsafeTo`, a successful mmap read avoids ReadAt syscalls; grouped compressed mmap reads compute the whole-record CRC **before** grouped-cache lookup ([CRC](/private/tmp/gomap-qs-5005-verify/TreeDB/internal/valuelog/reader_mmap.go:850), [lookup](/private/tmp/gomap-qs-5005-verify/TreeDB/internal/valuelog/reader_mmap.go:938)). If mmap is unavailable/out of range/dead-mapping capped, CRC-enabled `ReadUnsafeTo` falls through to the generic scratch decoder ([fallback](/private/tmp/gomap-qs-5005-verify/TreeDB/internal/valuelog/manager.go:771)): header/payload ReadAt, whole-record checksum, then grouped decode for the requested subvalue ([generic reader](/private/tmp/gomap-qs-5005-verify/TreeDB/internal/valuelog/reader.go:1205)). That path does not use the File grouped-cache helper. CRC-disabled fallback can use the helper, although its header/frame/table reads precede the cache lookup ([helper](/private/tmp/gomap-qs-5005-verify/TreeDB/internal/valuelog/manager.go:783)).

These are plausible sources of repeated decode/checksum CPU and cached read syscalls. The reported ~7M read syscalls are not attributable from source alone: active integrity settings, mmap misses, leaf/grouped-cache counters, and stacks are needed. Fresh per-scan page memos, per-page segment tallies in multi-root projection, and copied resource descriptors also imply allocation churn; whether they explain peak memory requires allocation/heap evidence. No memory fix is established here.

## Bounded options, ranked by evidence and risk

**1. First causal experiment: larger existing batch size on an isolated offline copy.** `treemap compact` opens `OpenBackend` and already exposes `-rewrite-batch-size`; it passes that value directly to CompactStorage ([CLI](/private/tmp/gomap-qs-5005-verify/TreeDB/cmd/treemap/main.go:500)). CompactStorage uses the same online rewrite implementation, with the existing maintenance lock already held when applicable ([call](/private/tmp/gomap-qs-5005-verify/TreeDB/db/compact_storage.go:535)). Compare 256 against a bounded size such as 4096, holding source selection/configuration constant. This preserves the exact scanner and should reduce publication count proportionally; increased swap/key-arena/apply footprint and longer cancellation/lock boundaries must be measured. Treat it as a diagnostic/configuration option, not authorization to enlarge defaults for online/background callers. Accumulating all pointers in one commit is not yet justified by memory, cancellation, crash, or online contract evidence.

**2. Candidate optimization: supply exact logical pointer deltas plus certified new raw-leaf dependencies.** Simple logical counts cannot describe raw `LeafLogPtr` dependencies, which is the explicit reason projection is disabled ([reason](/private/tmp/gomap-qs-5005-verify/TreeDB/db/durable_root_runtime.go:286)). Existing ordered multi-root publication already composes precise logical changes with predecessor raw dependency reuse and created/current leaf segment admission ([producer identity helper](/private/tmp/gomap-qs-5005-verify/TreeDB/db/ordered_root_publish.go:1191), [ordered exception](/private/tmp/gomap-qs-5005-verify/TreeDB/db/ordered_root_publish.go:1545)). The reuse planner recaptures stable frontiers, rejects unreportable/unknown current segments, and projects negative logical counts exactly ([planner](/private/tmp/gomap-qs-5005-verify/TreeDB/db/durable_root_runtime.go:669)). This is a concrete seam for a rewrite-specific prototype, **not** proof that enabling the gate or clearing `requiresCandidateProjection` is sufficient. Ordinary destructive DB-root publication deliberately scans for exact raw-leaf retirement; system descriptor transitions can attach nested references outside an apply-local delta. Any rewrite fast path must include newly created outer-leaf identities, use matched swaps only, reject stale tracker bases, cover system/collection aliases, and finish with an exact closure boundary that removes obsolete raw dependencies. Otherwise predecessor supersets can accumulate across the rewrite and worsen disk/resource retention. Preserve existing fallback on incomplete evidence.

**3. After profiling: reduce redundant candidate passes or batch verified grouped reads.** The candidate scanner's registration frontiers exist to discover unregistered canonical files before descriptor decoding. Combining its final count projection with earlier work requires preserving this discovery/rebind order and matching final counts; it is not a safe blind deletion of scans. Verified grouped batching could amortize CRC/decode without changing integrity guarantees, but it attacks a constant factor and should follow proof of stack/counter dominance.
