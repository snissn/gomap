## What must change, and why

Current inline finalization captures external resources at `TreeDB/db/db.go:3659` before it stages pending leaf membership at `:3736`; queued publication likewise captures at `root_publication_activation.go:760` before `prepareVisibleInstallV1` stages at `:390`. Thus a root can carry the predecessor immutable manifest while later post-work advances the operational view. Both capture routes must consume one already-validated manifest result; neither may independently discover new membership after capture. Preserve the existing registrability filter until meaningful RED selects its supported-contract scope: this design addresses ascending capture/stage ordering, not arbitrary lower-sequence history.

The existing private `prepareLeafGenerationManifestStableCandidate` (`leaf_generation_manifest_stable_prepare.go:234`) is the producer seam: actual immutable contents, exact revision/digest/identity, real content and namespace synchronization, no DB-visible installation, and exact unpublished-abandon authority. Run it with no DB/write/commit/root-build serialization lock, durable publication gate, group mutex, or publish-prepare guard held. A retained BuilderToken is admission/resource ownership, not permission to hold those locks during I/O. Do not use the public wrapper at `:190`: it acquires write/commit serialization around this helper. Do not use an empty reserved file or ContentSynced=false shortcut: prior inquiry found no complete reserved-name/owner/retry contract, and deferred content sync alone cannot supply durable namespace authority.

## One shared protocol

1. **Build and freeze owned inputs.** Keep the exact index generation and registered base root/read/resource pins, teardown admission, BuilderToken where already available, user/system roots and base CommitSeq, private allocated page IDs, deferred old-page retirements, value-ref delta, raw producer and dictionary tokens. Apply remains ordinary; actual producer writes/registration remain the source of membership. Freeze producer capture into exact tokens before releasing its owners (`apply_leaf_resources.go:334`); keep those tokens through detached preparation. Do not submit old-page retirements, install visible state, append a command frame, or construct an allocator prepared candidate yet.
2. **Select a semantic membership candidate while serialized.** Snapshot the exact operational manifest basis plus pending IDs/attribution for the prospective next CommitSeq using the existing staged-result seam (`leaf_generation_manifest.go:614`). Retain candidate, raw IDs and exact pending IDs; obtain membership needed by the private output from existing producer evidence. A changed=false result can reuse an existing token only when the normal exact capture validates that the selected immutable token covers that same semantic view and all required raw IDs. If it cannot, fail closed; do not treat an operational pointer, compatibility file or filename as authority. Membership unchanged must not cause a new immutable revision solely for unrelated entry values, time or CommitSeq.
3. **Detach before all waits.** Transfer the private attempt to its finalizing owner and release all actual locks/guards listed above. Retain base pins and exact resources; do not retain `publishPrepareMu` merely to block GC through preparation. On changed membership, call the private stable helper once. Existing store serialization allocates the actual revision; use the returned persisted candidate (not a predicted revision). The helper may update compatibility storage, but that does not install a root or replace either sealed slot's exact token.
4. **Reacquire and validate, without I/O.** In existing path lock order, verify open/admitted and non-poisoned runtime, identical index identity and visible user/system roots/base CommitSeq, operational manifest basis identity/semantic contents, root-specific conditional/negative coverage, and exact producer/pending attribution. Recompute the in-memory staged candidate and require identical semantic membership to the prepared candidate, allowing only the returned actual immutable revision. Any newly needed mapping, changed generation state, or changed base requires abandon/rebuild; never patch an immutable prepared token in place. No blanket drain of pending IDs. Compare exact manifest token revision/identity/digest and actual required raw IDs as well as root IDs; root ID alone is ABA-unsafe.
5. **Complete pre-publication producer waits outside locks.** Release root serialization again for `prepareFlushApplyPublish` if it can sync, and for synchronous command-WAL append/dependency/flush waits. Preserve the actual WAL publish admission/order and one intent identity. Then reacquire and revalidate the same basis before candidate capture. Before an assigned LSN, a stale serialized attempt can use its existing retry loop; an unaccepted stale group must return its pre-append stale error and let the owner rebuild the whole group, not replay already-closed member batches internally. After a frame is assigned, failure/staleness must retain that LSN and the existing poison/reopen rule; never silently retry/append twice. This second validation is necessary because a maintenance/vacuum publication can change the basis during the unlocked wait. It is a fail-closed race outcome, not a lock exception or a promise of unchanged contention behavior.
6. **Handoff exactly once.** Merge the new manifest closure with the owned producer resources and inherited exact dependency closure through existing move-only resource APIs. Pass the returned candidate manifest and raw-ID list to the existing finalizer, with `leafManifestAlreadyPersistent=true`. Inline and queued capture must select this exact manifest revision instead of including a conflicting predecessor manifest for the new root; inherited raw/dictionary dependencies and both older durable-slot closures remain pinned. The pending stage in both consumers becomes validation of the already-prepared result, not another mutation/persistence decision. On acceptance install that exact operational view and clear only validated pending IDs. Post-work may build rebuildable record-length indexes; it must not mint a second authoritative manifest revision (`command_wal_publish.go:92`). Keep existing CRC, seal/meta slot choice, dependency-before-index/meta ordering, WAL applied-range/ACK ordering and late fences.

## Rollback limits and stop conditions

`allocTracker.FreeAll` (`alloc_tracker.go:52`) calls Free only for IDs allocated by that attempt. In COW mode `Allocator.Free` (`freelist/allocator.go:803`) conservatively retires those IDs through `retireCOWLocked` (`allocator_cow.go:334`). It does not rewind shared transaction/high-water state or immediately recover physical tail bytes. That is the correct existing optimistic abandon model to reuse for serialized private output: never free the old root's deferred retirement list. Release producer/pin/delta handles once; preserve teardown until attempt cleanup joins. Cleanup errors are real errors, not successful retries; FreeAll clears its list before attempting each Free, so do not invent an idempotent second cleanup pass.

Do not call `PrepareCOWCandidateV1` before detaching: its prepared barrier makes later Alloc/Free wait (`allocator_cow.go:243`), while rollback snapshot is taken after Apply (`:388`). It neither supplies complete Apply rollback nor safely lets competitors wait under locks that the preparing writer later needs. Existing candidate materialization/abort stays after validation at its original ownership boundary. Accepted output is never tracker-freed, even if acknowledgment wait returns an error. A transferred manifest token is released/retained by its candidate; an untransferred revision may only be cleaned with `abandonUnpublished` exact identity/revision authority outside locks. Never restore a newer compatibility view, delete referenced older revisions, weaken either slot/pin/replay/dictionary checks, or manufacture a missing mapping.

There is one additional concrete integration obligation: `appendRawKVCommandWALIntent` is not just an in-memory append. Its existing implementation (`command_wal_raw.go:2722`, `:2801`) synchronizes dependencies and flushes/syncs the journal when requested. Calling it under commit/write serialization would violate the requested strict wait rule. The protocol above moves that existing call outside those locks and explicitly preserves post-append poison/recovery. If the all-three-path WAL admission owner cannot be retained across that detached interval, this is a **hard implementation blocker**: a manifest-only finalizer patch cannot be called coherent. No new WAL admission API or exception is assumed here.

The minimum implementation proof obligations are: serialized tracked abandon frees only new IDs; group Close/finalizing races have exactly one owner; base/index/manifest drift during detached prepare rejects before capture; physical prepared-token cleanup does not undo a newer compatibility view; changed=false retains exact token with no new manifest sync; changed=true pins exact new manifest in inline and queued roots; both slots and old readers remain readable; command-WAL dependency-before-frame, assigned-LSN failure poison, applied ranges and ACK remain ordered. Existing ascending writer-ACK test must first reach real setup authority and causal phase. Lower-sequence controlled case remains inquiry. Until those tests and meaningful RED exist, this remains a conditional design, not selected production repair.
