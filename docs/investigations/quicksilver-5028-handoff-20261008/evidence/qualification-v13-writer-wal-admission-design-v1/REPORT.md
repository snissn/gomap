# Detached writer WAL-admission contract

Source-only answer at root-provided B `a6b778ffeb9a401848d5eaf6d177547a5f21aef8`. No implementation, runtime, performance, numerical, qualification, product or merge acceptance; held #5004/PR #5006 excluded. No Git/Go/test/native/network/state operation. The earlier repair design remains unchanged.

**BuilderToken + teardown/read admission + an intent/LSN are sufficient to retain lifetime, but not to retain WAL ordering.** The existing *raw publish/staging guard* is the missing distinction. Ordinary nonphysical Batch.write already owns the needed guard across both optimistic and serialized attempts. Generic physical batches and RootPublicationBuildGroup do not bind one, so the same conclusion cannot be extended to all three paths using only their current handles. No new WAL-ordering primitive is necessary; the missing all-path contract is an explicit live admission borrow/ownership handoff into physical/group finalization, or an existing caller-owned prefix protocol that deliberately permits drift and fails/rebuilds without ACK.

## Definite supported ordinary-write protocol

`batch.go:313–342` acquires `LockCommandWALPublishWithBarriers()` before constructing the raw intent and defers its returned unlock until the whole `writeWithCommandWALIntent` completes. The guard owns teardown RLock, exclusive raw admission and exclusive `commandWALRawPublishMu` (`command_wal_barrier.go:255–298`). Retain that exact outer guard across detached manifest/producer waits; release DB/write/commit/root-build locks, durable publication gate, group/private mutex and publish-prepare guard. This is existing WAL append/publish ordering admission, not a retained root-build lock or a new dependency-wait exception. Backend raw append entrypoints already perform synchronous WAL dependency/flush work while owning this guard without root construction locks (`command_wal_raw.go:1409`). Do not release/reacquire it or run barriers recursively.

Both optimistic and serialized paths can retain the same guard because they are called inside that outer scope. Before LSN assignment, private-output/base drift can abandon and use existing optimistic/serialized retry ownership; the single intent is reused. The intent is not structurally immutable: append updates LSN/covered range, consumes dependency/RID-cache resources and clears a finalize callback. It must remain single-owner; its payload/borrowed entries must remain valid until actual append. The guard supplies ordering, not a concurrent-use license for this pointer.

With root locks released, run exact conditional immutable manifest preparation and necessary producer waits; reacquire/revalidate before append selection; release root locks for the existing synchronous append; reacquire/revalidate before candidate capture. Another well-behaved raw command writer cannot append/publish under that held raw guard. Non-WAL physical/maintenance publication can still change the root/index basis, so validation remains mandatory. On a newly assigned LSN followed by stale/error before acceptance, call the existing post-append poison path, retain the assigned frame/resources for recovery, return the error and release owned output/guard. Do not append a replacement or ACK this attempt. Once the candidate is accepted, no private-output rollback or poison solely because a later admission/durability wait errors; preserve `post.accepted` and the normal acknowledgment outcome.

This resolves the earlier report's WAL stop condition for ordinary nonphysical serialized and optimistic/queued writes using existing ordering admission, with no new WAL guard API. BuilderToken is separate: it counts active builders, allows nesting, and is consumed only at `Coordinator.EnqueueBuilt` (`admission.go:87–131`); it does not reserve an LSN or exclude another builder. `activeBuilders==0` gates publisher readiness (`coordinator.go:707`), so do not wait for coordinator publication while retaining an unconsumed builder. Manifest/producer synchronization is not such a coordinator wait. Acquire/revalidate the runtime's BuilderToken at its existing stage, retain it through private preparation if acquired, consume/release exactly once on normal handoff/abort.

## Preassigned LSN and physical/group boundary

The invariant fixture calls `AppendRawKVCommandWALOrderedEntries(entries,true)` and only *after that call returns* constructs physical batches/groups (`external_manifest_writer_invariant_test.go:59–85`). The append helper releases its own raw guard on return. `SetCommandWALPublish` (`batch.go:121–146`) only creates a local `{lsn,coveredRange}` record; it does not attach the original intent, raw guard, producer dependency ownership or teardown lease. Its public contract explicitly says already-appended LSN. The fixture is sequential and is valid for its causal invariant scope; it is not a concurrent detached-admission test.

At `appendCommandWALIntentWithTiming:2654`, an already-assigned non-replay intent returns its LSN after poison checks. It performs no new append and no independent proof that numeric LSN has durable bytes. The fixture's actual append used true; a generic SetCommandWALPublish caller must provide its own actual preceding append/prefix authority. Do not convert WriteSync or a supplied number into a fabricated durable-frame witness.

`Batch.write` bypasses raw admission for physical batches and retains only teardown (`batch.go:289–328`). Build-group dispatch occurs even before that branch. `beginRootPublicationBuildGroup` owns teardown, snapshot/read/registry pins, a BuilderToken and write/durable gates (`root_publication_build_group.go:89–185`), but no raw guard/intent. Its final batch accepts numeric coverage. Therefore dropping the root locks permits unrelated raw writers to append; a writer may also publish a different visible base. Pins keep the old output readable, not current. BuilderToken may delay durable coordinator publication, but does not prevent other candidates becoming visible or another LSN being assigned.

Numeric applied-range validation is a rejection guard, not ordering admission: `validateCommandWALPublishLocked`/`validateContiguousAppliedCommandLSN` (`command_wal_publish.go:342`) reject regression/gaps/stale coverage. Publishing N+1 cannot claim N merely because a manifest exists; N cannot replace a successor root or old index after drift. With exact base validation and no ACK on rejection, this can fail closed. Existing group finalization sets `commandAppended=true` even when the append call simply returns its preassigned LSN and poisons if `post.accepted` is false (`root_publication_build_group.go:401–460`). Moving preappend drift outside that region must not silently make a formerly assigned frame retryable: retain its actual owner/prefix for recovery or explicitly use an existing captured-prefix retry contract.

Cached prefix flushing is a distinct existing authority. `command_wal_public_cached.go:352–422` fixes an operation/frontier cut, permits later writes into the fresh generation, and returns only the contiguous captured prefix. `caching/cow_flush.go:181–249` owns the captured immutable cut and treats group acceptance separately from later handoff errors. Later WAL append alone does not invalidate that prefix. It does not authorize overwriting a changed backend base or make a generic numeric SetCommandWALPublish token into a live global ordering lease. Preserve the retained cut/prefix on unaccepted failure; never expand its LSN coverage to newer mutations to make validation pass.

## Smallest necessary all-three-path admission contract

For a design that excludes unrelated WAL publication during detached preparation, acquire/retain an existing raw/staging ordering guard **before** entering the physical writer/group's root locks. Use barrier-aware admission only at its established pre-build boundary; do not invoke barriers inside a cached flush that they might recursively drain. A caller that already holds staging/prepared admission must lend that exact live owner rather than reacquire raw admission.

The narrowly missing internal bridge is: bind DB identity, live ordering owner, exact assigned intent or captured LSN-prefix contract, and borrowed teardown ownership into the physical attempt/group; retain/borrow the guard until rejection or accepted handoff and until the caller's required ACK boundary; validate ownership once, never synthesize it from LSN, and release only by its real owner. Existing `CommandWALStagingGuardV1` has DB validation, append ownership, exact intent attachment and capture borrowing (`command_wal_barrier.go:375–464`), but neither physical Batch nor group accepts that ownership. A private extension of their admission/finalization input, reusing those checks, is necessary if that stronger contract is required. No new production export or scheduler is needed.

A borrow must also avoid recursive teardown RLock: physical Batch.write and beginGroup currently acquire it themselves; a queued Close writer can make a second read acquisition deadlock even when the caller owns the first. Give the admitted attempt explicit borrowed-teardown ownership, matching existing closeTeardownPinned semantics, instead of blindly nesting read locks. Group finalizing ownership must additionally prevent Close from freeing the detached attempt's resources. The bridge must reject a released/foreign guard and ambiguous prefix; it cannot obtain a missing guard by blocking under root locks.

Thus the answer is precise: **existing outer raw guard supports the detached ordinary-write repair; the three handles in the question alone do not.** A generic concurrent preassigned physical/build-group repair needs this small admission-borrow bridge (or must explicitly keep the existing captured-prefix fail/retry owner and accept fail-closed drift). There is no source-supported claim that the current group API already transfers that guard. This is the remaining implementation contract, not a reason to weaken slot, CRC, WAL-range, poison or ACK gates. Required discrimination is an interleaving test for ordinary held guard, preassigned physical/group without guard, transferred/borrowed guard, and post-assignment drift; no such test was run here.
